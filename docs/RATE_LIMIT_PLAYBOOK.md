## 0. 结论先行

**你遇到的绝大多数中断，并不是 IP 级限流。**

在 1997 次查询构成的失败样本里：

| 归类 | 次数 | 占比 | 真实性质 |
|------|------|------|----------|
| `SessionBusyError`（自家 profile 互斥锁未拿到） | 147 | 38.9% | **纯客户端问题**，与对方服务器无关 |
| 日历接口 `444 非法链接`（缺入口页会话预热 / as-sdk 签名） | 90 | 23.8% | **会话层校验缺失** |
| 列表页 `HTTP 202` 未取得响应 | 55 | 14.6% | 边缘节点软拒（部分确属频率） |
| 官方页面要求验证或登录（challenge） | 86 | 22.8% | 人机验证 / 登录墙 |
| **真正的 HTTP 429（IP 频率限流）** | **1** | **0.3%** | 唯一一条真·限流 |

即：**约 63% 的"被限流"是自家链路顺序错乱导致的次生失败**，另有 22.8% 是会话/验证门。
真正花钱也未必买得到解的"IP 被封"，在样本里占比不到 1%。

所以正确顺序是：**先修因果链，再谈降频；最后才考虑换出口 IP。**

## 2. 限流的七类成因（按防线层级）

真实 OTA 站点对单 IP 的拒绝通常落在四个层级，症状完全不同，解法也不同：

### L1 · 传输 / 边缘层（CDN · WAF）
- **观测**：`HTTP 444`（nginx 关闭连接不响应）、`HTTP 202` 但 body 为空、TLS 握手特征拒绝、`403`
- **触发**：单 IP 短时间连接数、请求头完整性、`Accept-Language`/`sec-ch-ua` 组合可疑
- **你的证据**：日历 444 ×90、列表页 202 ×55
- **解法归属**：会话完整性优先，不是加代理

### L2 · 频率层（IP / 接口 QPS 配额）
- **观测**：`HTTP 429` + `Retry-After` 响应头；或接口返回 `{"code":"TOO_MANY"}`
- **触发**：单位时间请求数超过 token bucket
- **你的证据**：**仅 1 次**
- **解法归属**：降速 + 指数退避 + 尊重 `Retry-After`

### L3 · 会话 / 指纹层
- **观测**：要求登录、跳滑块、"操作过于频繁请稍后再试"、低价接口返回非法签名
- **触发**：无 Cookie 或使用无痕冷上下文；Canvas/WebGL/JA3 指纹；headless 特征（`navigator.webdriver`）
- **你的证据**：要求验证或登录 ×86；同程 444 明确是 as-sdk 页面签名缺失
- **解法归属**：**会话预热 + 持久 profile + 串行** —— 本项目主要战场

### L4 · 业务风控层
- **观测**：能拿到数据但字段被污染（价格错乱、随机缺失）；或仅特定高价线路返回结果
- **触发**：账号信用模型、历史行为序列
- **解法归属**：不在本题范围（需真实账号信用积累）

### L5 · 客户端自身串行冲突（**本项目头号问题**）
- **观测**：`SessionBusyError: 会话正在登录或采集`
- **触发**：`crawlers/base.py:238` 的 `_PROFILE_LOCKS` 互斥锁未抢到
- **你的证据**：**147 次，占全部失败 38.9%**
- **因果链**：同 profile 并发/排队 → 抢不到锁 → **跳过入口页会话预热** → 后续请求全部 `444 非法链接` → 表象酷似"IP 被封"
- **解法归属**：调度层可用性与重复请求治理，零成本

### 3.1 出口类方案细分（H 项拆解）

把 H 拆成五档——**它们解决的不是同一个问题**，成本差两个数量级：

| 方案 | 实现难度 | 稳定性 | 月成本（量级） | 对国内 OTA 的实际效果 | 判断 |
|------|---------|-------|--------------|--------------------|------|

| 按渠道分配出口（宽带 + 热点双线） | 中：`crawler.proxy` 需从全局单值改为 per-platform | 中 | ¥0 | 把"5 站共用 1 个 IP 画像"拆成 2–3 份 | 进阶，收益稳定 |
| 住宅代理池 | 中高：选池、验活、控并发 | 中偏低：国内池质量参差、IP 复用率高 | ¥50–500 | 仍带着 headless / 深链 / 冷上下文特征，**换 IP ≠ 换身份** | 长期跑量再评估 |
| 机房代理 / 轻量云多机 | 中 | 低：IDC 段风控分天然高 | ¥24–100 每台 | 多数站点比家宽更容易被拦 | 不划算 |

## 4. 落地清单（按优先级）

### P0 · 立刻改的三个数（`config.yaml`）

> **已落地（2026-10-27 核对 `config.example.yaml`）**：`interval_minutes: 30` ✓、`jitter_minutes: 5`（本节建议 8，取 5 亦可——关键是打破精确周期）、`scan_quiet_start/end: 01:00/07:00` ✓。本节保留当初的推导，数值以配置为准。

```yaml
schedule:
  interval_minutes: 10   →  30      # 实测单轮需 6.3 分钟；留出 ≥3 倍冷却
  jitter_minutes: 0      →  8       # 关键：打破 16.3 分钟的完美周期
```

加上**夜间扫描静默窗口**（当前 01:22–07:19 全程满速，这是最刺眼的异常）：

```yaml
schedule:
  scan_quiet_start: '01:00'
  scan_quiet_end:   '07:00'         # 注意：现有 quiet_start/quiet_end 只管推送，不管抓取
```

> 机票价格在凌晨几乎不变动，停扫 6 小时对监控价值无损，对降风险收益最大。

### P1 · 熔断退避（防止把"软失败"升级成"硬封禁"）

> **时效说明（2026-10-27 核对）**：下面这张表是**设计初稿**，其中的状态名
> `ip`/`captcha`/`part`/`maintenance` **不是当前代码的取值**。现行实现见本节末的
> 「现行实现（真值）」——判断"现在会怎么退避"以那张表为准。

#### 现行实现（真值，`core/pacing.py` `classify_failure` + `ChannelBreaker`）

分类函数输出只有 4 个非空值 + 空串；空串表示「不是对方拒绝」，**不触发任何冷却**：

| 归类 | 触发依据 | 熔断行为 |
| --- | --- | --- |
| `soft`（软拒） | 路径状态含 `soft_reject`，或 note 含 软拒 / 444 / 202 空 | **不做 IP 式冷却**；置 `needs_warmup`，下一轮先养会话再查。优先级最高、短路后续判断 |
| `ip` | note 含独立数字 403/429（`\b403\b`/`\b429\b`）或 风控/限流/179991/ip封 | 阶梯退避 `base·2^(n-1)`，封顶 `cap`；累积 `strikes` |
| `captcha` | 路径状态含 `blocked`，或 note 含 验证码/滑块/人机验证/访问验证/安全验证/challenge/captcha | 同 `ip` 的阶梯退避 |
| `login` | 路径状态含 `login`，或 note 含 请登录/未登录/需登录/登录失效/会话失效 | **固定冷却**（默认 900s），不累积 strikes，打 `needs_login` |
| `busy` | 自家 profile 锁冲突（`SessionBusyError`） | **0 秒**，本轮让位即可（重试无意义） |
| 空串 | 超时、解析失败、真无票 | 不冷却——重试不会变好，但也没有理由停手整个渠道 |

两条容易踩错的：
- **软拒优先短路**：444/202 字样同时命中"ip 标记"，若不先判 soft，会把"会话没养熟"误冷却成"IP 被限流"，拖垮整家渠道。
- **403/429 必须按独立数字匹配**：路径详情里带价格（如 `￥1403`）时，裸子串会把正常出价当成限流信号。

`core/health_diag.py::classify_round` 已经在产出 `ip` / `captcha` 两类卡片，
直接拿来做驱动即可：

| 渠道状态 | 动作 | 退避 |
|---------|------|------|
| `ip` / `captcha` | **本轮立即放弃，不再重试** | 2^n 轮（上限 8 轮），且期间完全不发请求 |
| `part` | 保留上一轮结果，不重登 | 1 轮 |
| `SessionBusyError` | **跳过该渠道本轮**（下轮自然补上），**不要重试** | 0（不是服务端拒绝，重试只会继续抢锁） |
| `maintenance` | 等待恢复 | 已有锁存逻辑 |

**核心原则：面对拒绝信号，第一反应必须是"退"，不是"换姿势再试"。**
重试风暴会把单次软失败放大成持续 30 分钟的高速冲击，这是唯一能把平台从"限你"升级成"封你"的动作。

### P2 · 两级拉取（最大的请求量杠杆）

项目里已经有 `cal`（低价日历）与 `detail`（航班明细）的分层标记，直接据此做配额：

```
第 1 级  低价日历 / 低价榜      廉 · 高频（每轮都做）        ← 一个请求可覆盖 30 天
第 2 级  真实航班明细           贵 · 仅触发（默认不做）      ← 5 平台 × 全日期是大头
```

触发条件建议：`|日历最低价 − 心理价位| ≤ 10%` 或 `较上次入库价变动 ≥ threshold`
时才在该轮拉取对应「渠道 × 航线 × 日期」的明细。

按当前 6 航线 × 7 日期 × 5 平台的规模估算，**明细请求量可下降一个数量级**，
而错过降价的概率几乎不变（日历价本身就在告诉你该不该细看）。

### P3 · 会话卫生（专治 444）

`crawlers/tongcheng.py:401` 的注释已经写明答案：

> 入口页养会话（as-sdk 初始化 + cookie 下发；缺这步 = 444）

因此要保证：

1. 同一 profile 在任一时刻**只有一个**任务在跑（消除 `SessionBusyError` 的根）；
2. 会话预热步骤**不可跳过**——抢锁失败时应整轮让位，而不是带着裸 cookie 继续打；
3. 维持持久化 `user_data_dir`，避免每次冷启动重建指纹。

### P4 · 各渠道错峰

不要让 5 个平台在同一秒开跑。给每个渠道一个固定偏移（如 `hash(platform) % 5 × 25 秒`），
把"5 个平台同时冲击 5 个不同的 WAF"变成均匀铺开的低幅背景流量。

## 6. 边界与合规

本手册的所有建议都建立在"降低负荷"而非"规避防护"之上。请守住以下边界：

1. **遵守 `robots.txt` 与各站服务条款。** 监控类自用不等同于授权采集；
2. **数据仅限个人学习与自用**，不得对外再分发、转售或以 API 形式提供给第三方；
3. **不破解验证。** 遇滑块/人机验证应当"停手"，而非找打码服务绕过——这是本项目明确不做的一条；
4. **不伪造身份。** 不冒充特定真实用户、不使用他人账号凭证抓取仅登录后可见的内容；
5. **不做高频轮询公共接口。** 把自己当作一个礼貌的用户：一个人一分钟点几次搜索，你就发几次请求；
6. **异常即退。** 收到 429/444/403/验证页时立即降低频率并退避，而不是换 IP 继续。

> 补充：多数航旅平台都有公开的开放接口 / 企业合作通道。若未来有预算，
> 走官方通道永远优先于任何技术手段。

## 9. 已落地实现（1–6 区 · 2026-10-25）

六项全部实现为「可配置 + 可观测」，缺省值保持旧行为；改配置保存即热生效，
改代码需重启进程。

| 区 | 能力 | 配置键（config.yaml） | 落点 | 观测 |
|---|---|---|---|---|
| 1 | 夜间静默窗 | `schedule.scan_quiet_start/end` | main `_sweep_inner` 顶部 | 日志 `[节流] 夜间静默窗…`；`/api/pacing.quiet` |
| 2 | 熔断退避 | `crawler.breaker.{enabled,base_s,cap_s,login_cooldown_s}` | `core/pacing.py::ChannelBreaker` | 日志 `[节流] X 命中ip，熔断 Ns`；`/api/pacing.channels` |
| 3 | 两级 TTL | `schedule.{fast_ttl_min,slow_ttl_min,near_ratio}` | `core/pacing.py::tier_of/plan_query` | 轮末 `[节流] 计划 N 次…`；`/api/pacing.last_round` |
| 4 | 会话卫生 | 恒开（无开关） | `crawlers/base.py::safe_fetch` + main 整批持锁 | 日志 `[会话] X profile 正被占用…`；`last_round.busy` |
| 5 | 令牌桶 + 错峰 | `crawler.rate.{min_gap_s,per_minute}`、`schedule.stagger_seconds` | `core/pacing.py::TokenBucket/stagger_offset` | 日志 `[节流] X 起跑偏移`；`/api/pacing.bucket` |
| 6 | 出口自检 | `crawler.proxy`（已有键） | `webui.py::_exit_check` | 配置页「出口自检」按钮 → `/api/exit-check` |

### 并发锁约束（同渠道管控）

- **闸门与等待全在 `channel_slot()` 之外**：熔断判定、令牌桶等待、起跑错峰
  都不持锁——持锁睡眠会把 5 家渠道串成一条队（旧 310s 预防等待的教训）。
- **同渠道多返程日整批持锁**：避免释放锁后被别的查询插队，插队会打断入口页
  预热链（444 的直接成因）。
- **`SessionBusyError` 只让位**：`safe_fetch` 置 `last_busy`，main 看到就跳出
  返程日循环、不重试、不冷却——用自家锁冲突去惩罚对方站点是双重错误。

### 默认值与本机取值

```
代码默认  fast_ttl 15 / slow_ttl 120 / near 0.15 / stagger 0
          min_gap 0 / per_minute 0 / breaker 开(base 300, cap 3600)
          login_cooldown 900 / warmup 开(qunar, fliggy, tuniu)
本机配置  interval 30 / jitter 8 / 静默 01:00–07:00
          stagger 25 / min_gap 3 / fast 15 / slow 120
```

> 判据来源：`core/pacing.py` 的 `DEFAULTS`（`fast_ttl_min` / `slow_ttl_min` / `near_ratio` /
> `stagger_seconds` / `min_gap_s` / `per_minute` / `breaker_enabled` / `breaker_base_s` /
> `breaker_cap_s` / `login_cooldown_s` / `warmup_enabled` / `warmup_platforms`）。
> 增删任何一个键都要同步这一块——门禁 `test_playbook_defaults_block_matches_code` 会对着代码比。

`fast_ttl` 必须小于「interval − jitter」，否则早到的轮次会被 TTL 挡掉——
这是唯一一个配错会"看起来像没扫"的键。

## 10. 第二轮：PC/H5 可观测 · 可干预 · 降风控（r370）

准则只有一条：**成功率↑、风控↓**。所以这一轮不动"更多数据"，只做三件事。

### 10.1 让服务端自己说等多久（L2 补完）

`Retry-After` 是唯一"对方明说"的配额信号。之前全仓 0 处解析，全靠自算 2^n。

- `core/pacing.parse_retry_after()`：秒数 / HTTP-date 双形态，向上取整、封顶一天；
- `crawlers/base.py`：`new_page()` 给每个页挂 429/503 响应监听，命中即写
  `self.retry_after_s` 并 WARNING 留痕；
- `ChannelBreaker.trip(retry_after=)`：**服务端指令优先**——比阶梯长就照它
  （可超过自设封顶），比阶梯短则取长的（提前回来只会再撞一次）。

### 10.2 抹掉"深链直入"指纹（L1/L3 补完）

`warmup()`：每轮每渠道首次使用前，先打一次首页再查深链。

```yaml
crawler:
  warmup:
    enabled: true
    platforms: [qunar, fliggy, tuniu]   # ctrip/同程在 fetch 内部自带
```

- 每轮每渠道**只一次**（`_warm_todo`），失败不阻断采集；
- 与采集共用 `channel_slot`，不会抢同一会话；
- 手动预热走同一函数与同一把锁（见 10.3）。

### 10.3 可观测：路径账（PC/H5 分开算）

`storage.path_stats(hours)` 聚合 `fetch_paths`：platform × entry_path × status。
`/api/paths?hours=24` 返回，配置页状态条渲染成
`携程 PC 100%(4) H5 100%(3) · 去哪儿 H5 0%(7) …`。

意义：**要收的是某条路，不是整家渠道**。实测本机库：
ctrip PC/H5 均 100%，fliggy PC 100%，qunar H5/API 0%——问题在 qunar 的入口，
把它整家降频是错杀。

### 10.4 可干预（三个动作，都持同一把渠道锁）

| 动作 | 入口 | 说明 |
|---|---|---|
| 解除熔断 | 状态条冷却中的渠道「解除」→ `POST /api/pacing/reset` | 人工确认对方已恢复时用，日志 `[干预] 手动解除…` |
| 手动预热 | 状态条「手动预热 qunar/fliggy/tuniu」→ `POST /api/channel/warmup` | 登录后/换出口后立刻喂 cookie |
| 出口自检 | 采集区「出口自检」→ `GET /api/exit-check` | 换热点/重播后确认公网 IP 真变了 |

三者都经 `channel_slot`，不会与定时采集并发抢会话。

### 10.5 遇到验证不再"静默失败"（现场 + 弹出窗口）

之前被滑块/登录墙拦住时，只有一行 WARNING，人再打开浏览器也没用——
因为采集用的是 `user_data/<platform>` 里的那份会话，另开浏览器就是另一个身份。

现在：

1. **留现场**：`rt["scene"][plat] = {at, kind, query, url, note}`，
   `url` 由 403/429/503 的响应监听（`base.last_block_url`）记住；
2. **一键去验证**：状态条上「去验证」→ `POST /api/channel/verify`
   → 用**同一份 persistent profile** 打开那个地址（可见窗口）；
3. **过完直接关窗**：`open_challenge_window` 在关闭时 `save_session`，
   cookie 落回采集档案，下一轮生效；仍冷却就点「解除」立刻重试。

边界：不代答验证、不接打码平台。人过验证，机器只负责"把现场端到人面前"。

### 10.6 指纹一致性（`crawler.stealth`，默认开）

只抹「自动化浏览器」的显式标记，不伪造账号、不改 IP：

| 面 | 处理 |
|---|---|
| 自动化标记 | `--disable-blink-features=AutomationControlled`；`navigator.webdriver` → undefined |
| 品牌面 | `window.chrome.runtime` 补齐；`navigator.languages` 锁 `zh-CN,zh` |
| 硬件面 | `platform/hardwareConcurrency/deviceMemory` 按 **UA 形态**一致（桌面 Win32/8/8，移动 iPhone/6/4） |
| WebGL | `UNMASKED_VENDOR/RENDERER` → 桌面 Intel UHD 630 / 移动 Apple GPU；并补 `WEBGL_debug_renderer_info` |
| Canvas | `getImageData` 抽样像素 ±1，**种子按 profile 固定**（同会话一致、跨 profile 不同） |

**移动 UA 必须配移动指纹**：iPhone UA + `platform=Win32` 是自相矛盾，
比不伪装更醒目。Canvas 用随机数反而更可疑（同会话两次读数不一致=机器特征），
所以用 profile 派生的确定性微扰。

这一项和「降频」是两回事：降频减少碰撞，指纹一致性避免把正常请求**误判**成机器人。

### 10.7 成功率保护（自动降频，不是熔断）

熔断只管"对方明确拒绝"（403/429/风控/验证）；**持续解析失败、空结果**不会
触发它，却同样烧请求。所以每轮从账本读一次 24h 成功率：

| 近 24h 成功率 | TTL 惩罚 | 效果 |
|---|---|---|
| ≥70% | ×1 | 正常 |
| 40–70% | ×1.5 | 慢半拍 |
| <40%（样本 ≥5） | ×3 | 明显收缩 |
| 样本 <5 | ×1 | 不判（防首轮误伤） |

口径：这里的「近 24h 成功率」是**原口径** `query_rate`（`main.py` 调 `pac.set_health(plat, node["query_rate"], …)`），
**不是**「在用口径」`query_rate_live`——罚速对该渠道的所有路径一律生效，不区分退役与否。
若要按在用通路罚速，属代码变更，需同时改这里与 SPEC §2.5 的消费方表。

`Pacing.set_health()` 写入，`plan_query()` 读它放大 fast/slow TTL；
状态条 `/api/pacing.channels[].health` 直接看得到 `rate/attempts/penalty`。

### 10.8 验证闭环：关窗即复位 + 单查探测（r373）

原先「去验证」只是打开窗口，人过完还得自己点「解除」，也不知道到底通没通。
现在关窗即视为「人认为搞定了」，自动做三件事：

1. `pacing.reset(platform)` —— 解除冷却；
2. `_probe_channel()` —— 用**同一条被拦查询**（`scene.query`）单查一次；
3. 结果写回 `scene[plat].verify = {at, ok, rows, note}`，状态条显示
   `验证后 ✓12条 / ✗未通过`。

没记录到查询时只做预热，不瞎猜一条查询去打。

### 10.9 命中验证自动开窗（`crawler.auto_verify`，默认关）

命中 `captcha` 时直接把窗口端到人面前，不用等人发现状态条变红。
同渠道 **10 分钟只开一次**（防连点/防多查询同时命中开一堆窗）。
默认关：上班时间被弹窗打断不是所有人都能接受；需要"无人值守也能被叫到"
就打开。

### 10.10 新鲜度（状态准确性的最后一块）

成功率好看但数据很旧 = 看起来正常其实没在采。`advise()` 现在会看
`path_stats.last_at`：最近一次成功超过 **120 分钟** → `state=stale`、
`action=probe`，提示「数据已 X 分钟未更新，点立即扫描或等下一轮」。
阈值刻意用固定 120 分钟而不是 2×interval——interval 可配置后它会把
"隔夜静默窗"也算成陈旧。

### 10.11 验证后补采（r374）

验证窗口关闭 → 探测通过后，自动把**本轮该渠道失败的查询**补采回来
（最多 8 条，避免变成第二轮全量），落库 + 刷新日聚合，日志
`[补采] qunar 补采 5 条查询，落库 37 条`。

告警仍走下一轮聚合：补采只为补数据，不为补推送——同一条降价推两遍比晚 30 分钟更糟。

### 10.12 每渠道独立节奏（`crawler.cadence`）

```yaml
crawler:
  cadence: {qunar: 60, fliggy: 0, ...}   # 分钟；0=跟随全局 TTL
```

它是**硬地板**：即使全局 TTL 已到（15 分钟），渠道自己没到 60 分钟也跳过。
适合"这家本来就慢/风控高，别用全局节奏催它"。

### 10.13 会话年龄看门狗（`crawler.session_max_days`）

profile 太久没更新会被站点当"新设备"。超过 N 天（默认 14）时，即便该渠道
不在预热名单，也会在下次采集前强制预热一次续期，日志
`[会话] qunar 已 16 天未更新，强制预热续期`。

### 10.14 案发现场 2.0（截图 + URL + 标题）

403/429/503 响应会打标记，在该次采集**关上下文之前**（同一个采集线程、
同一个 page，是 Playwright sync 唯一安全的截图时机）落盘：

```
debug/scene/qunar_20261025_171233_block.png
debug/scene/qunar_20261025_171233_block.txt   # url / title / at / block
```

只留 7 天自动清理。路径经 `/api/pacing.channels[].scene.files` 暴露。

### 10.15 按渠道绑出口（`crawler.proxy_map`）

```yaml
crawler:
  proxy: http://127.0.0.1:7897        # 全局
  proxy_map: {qunar: http://127.0.0.1:7891}
```

`proxy_map[渠道]` 优先于全局 proxy，浏览器与 httpx 共用同一个出口。
本机 Clash 是**规则分流**（实测：myip.ipip.net 直连出 58.246.127.206，
api.ipify.org 走代理出 64.186.225.7），所以给国内渠道单独指"国内节点"
才有意义；把国内渠道指到境外出口是升风控，不是降。

### 10.16 UA 与内核版本对齐（r375）

实测本机 Playwright Chromium 是 **151**，而 config 里 UA 写着 `Chrome/126`——
UA 头说 126、UA-CH/特性检测看到 151，这条矛盾比"版本新"更值得注意。

- `base.kernel_major()`：首次启动起一次无头浏览器读 `browser.version`，
  缓存到 `data/.kernel_major`，之后零成本；
- `_ua()` 把 UA 里的 `Chrome/x.y.z` 统一替换成真实主版本（`Chrome/151.0.0.0`）；
- 探测失败返回 0 → 退回原 UA，绝不阻塞采集。

### 10.17 手机 UA 不再注入 window.chrome

移动渠道用的是 iPhone Safari UA，而 `window.chrome` 是 Chromium 专属对象。
在 WebKit UA 上补 `window.chrome` 是自相矛盾的特征——现在按 UA 形态注入：
桌面补、移动不补（`__ADDCHROME__`）。

### 10.18 预热是否真生效：查风控 cookie

"访问过首页"不等于"被当成正常会话"。`warmup()` 现在检查风控 cookie：

| 渠道 | 判据（任一命中） |
|---|---|
| qunar | `QN1` / `QunarGlobal` / `QN205` / `QN277` |
| ctrip | `cticket` / `_bfa` / `MKT_CKID` |
| fliggy | `cna` / `_m_h5_tk` / `cookie2` |

一个都没落下 → WARNING `预热未拿到风控 cookie（…均无），深链大概率仍被拦`，
这是比"预热失败"更早、更准的信号（页面 200 但 cookie 没发，属于软拒）。

### 10.19 没有第二条宽带时，出口还能怎么换

| 手段 | 可行性 | 代价 |
|---|---|---|
| **PPPoE 重播** | 唯一可重复、可自证的动作 | 新 IP 多在同一个 /24，运营商维度仍可能被关联；面板「出口自检」会直接告诉你"IP 已变 / 未变 / 同 /24" |
| **手机热点 4G/5G** | 换 ASN（联通→移动蜂窝） | CGNAT 共享 IP，信誉通常更差，只适合应急 |
| **IPv6** | 部分站点 v4/v6 分开限流 | 同一 /64 会被关联，站点 v6 路径更少，收益不稳定 |
| **换 DNS/DoH** | 不是换出口，只换 CDN 边缘 | 成本最低，可能避开某个边缘节点的限流；不影响 IP 信誉 |
| 买住宅代理 | 不推荐 | 境外住宅代理对国内 OTA 更可疑，且成本高 |

结论：只有一条宽带时，**优先"降频 + 预热 + 验证闭环"，而不是换 IP**。
`data/exit_history.json` 记录最近 10 次出口 IP，重播后点一次自检即可判定
是否真的换了（含"同 /24"提示）。

### 10.20 渠道级告警（r376）

面板再准，人也得去看。连续 **N 轮零数据**主动推一条钉钉：

```yaml
notifier:
  channel_alert: {enabled: true, rounds: 3, cooldown_h: 6}
```

- 只统计**真的发过请求**的轮次：被节流/静默窗跳过的轮不算断供，

- 同渠道 6 小时内只喊一次；免打扰时段不喊（沿用 alerter 的 `_in_quiet`）；
- 文案带下一步：「控制台「节流状态」→ 看现场/去验证；验证通过会自动复位并补采」。

### 10.21 深链带 Referer（r376）

从首页点进列表的人有 referer，脚本直捣深链没有——这是最廉价的一条特征。
五个渠道的**列表页导航**现在都带自家首页 referer：

|---|---|
| qunar | `https://touch.qunar.com/h5/flight/` |

### 10.22 TLS/JA3 对齐（`core/net.py`，r376）

HTTPS 握手的 TLS 指纹（JA3/JA4）比 UA 难伪装得多，Python 的 ssl 栈有固定特征。
qunar 的直连 POST 现在走 `curl_cffi`（真 libcurl + Chrome 指纹配置）：

```python
from core.net import post
r = post(url, headers=h, payload=body_bytes, cookies=c, impersonate="chrome")
```

- 依赖**可选**：没装 curl_cffi 自动退回 httpx，行为与之前一致；
- `crawler.tls_impersonate` 可设为空串强制走 httpx（排障用）；
- 本机已装 `curl_cffi 0.15.0`，实测可用。

### 10.23 TLS/JA3 全渠道铺开（r377）

`core/net.new_client()` 是 `httpx.Client` 的等价替换，参数按 httpx 习惯传、
内部映射到 curl_cffi 的 `Session(impersonate=...)`：

| httpx 参数 | curl_cffi |
|---|---|
| `follow_redirects` | `allow_redirects` |
| `proxy` | `proxies={http,https}` |
| `trust_env` | 丢弃（curl 默认不读系统代理环境，同义） |
| `http2` | 丢弃（curl_cffi 自管 ALPN） |

已切换的 10 个会话点：**tuniu ×2**（国际/国内）、**fliggy ×1**（国际日历）、
**special ×7**（特价发现）；加上 qunar 直连 POST，全渠道的直连 HTTP 出口
都已对齐 Chrome TLS 指纹。

- 没装 curl_cffi → 原样退回 `httpx.Client`，行为与改造前一致；
- `crawler.tls_impersonate: ""` 可整渠道强制回退（排障用）；
- 单测覆盖参数映射与两条回落路径。

### 10.24 渠道自检按钮（r378）

配置页「节流状态」底部新增一行 **渠道自检：qunar · fliggy · ctrip · tongcheng · tuniu**。
点任意一个，后端跑**完整链路**（预热 → 一条真实查询），回报：

- 出数条数、每条路径的 `状态×行数`（如 `H5 ok×60`）
- 预热是否成功、拿到了哪些风控 cookie
- 被拒 URL、服务端 `Retry-After`、耗时

与定时采集共用同一把渠道锁，**不会和正在跑的轮次抢会话**；同一渠道同时只允许

接口：`POST /api/channel/probe {platform}`。

这就是「改完配置当场验收」的入口：换了出口、重登了账号、改了预热名单，
点一下就知道通不通，不用等下一轮、也不用看日志。

## 11. 第三轮：准确率、竞态与指纹幂等（r379）

准则不变：**先降负荷，再谈换出口**。这一轮不改抓取面，只修「看起来正常、
实际判错」的四个点。

### 11.1 查询口径 vs 路径口径

一条查询常常先试 H5 被拦、再走 PC 成功。旧账本按路径行算成功率，
会把「换路成功」记成 50%，进而触发整家渠道降频——正好把会出数的渠道
也罚了。现在 `fetch_paths.attempt_id` 把同一次查询的多条路径归为一组：

| 口径 | 字段 | 用途 |
|---|---|---|
| 路径尝试 | `paths[PC/H5].rate` | 判断哪条路该少走 |
| 查询成功 | `query_rate` | **渠道健康/自动降频只认它** |
| 明细成功 | `query_detail_ok` / `detail_ok` | 真实航班明细，日历不算 |
| 日历兜底 | `query_calendar_only` | 只拿到日历价时单独标「仅有日历」 |

### 11.2 国内/国际分开

路径汇总按 `core.intl.is_intl_route` 分 `dom` / `intl` 两套：

```
platform.scopes.dom.paths.PC   # 国内 PC
platform.scopes.dom.paths.H5   # 国内 H5
platform.scopes.intl.paths.PC  # 国际 PC
platform.scopes.intl.paths.H5  # 国际 H5
```

国内 H5 被登录墙拦住，不代表国际 PC 也坏；混在一起会把整家渠道判死。
自检接口也支持 `scope: dom|intl`，配置页可选「自动/国内/国际」。

### 11.3 新鲜度只看最近一次成功

`last_at` 是最近一次尝试，`last_ok_at` 才是最近一次成功。连续失败会不断
刷新 `last_at`，用尝试时间做新鲜度会把「一直没成功」误报成「刚刚更新」。
建议引擎现在只认 `last_ok_at`。

### 11.4 重启不重新全量打站

`Pacing.seed_fetch()` 在进程启动时从库里的**真实明细**（有起降时刻的行）
续上 `platform×航线×日期` 的最近价与时间。反复调试/重启后，TTL 仍然有效，
不会每重启一次就把全部查询重打一遍——这是「反复跑数据」最常触发的限流源。
日历行不参与续期：只拿到日历价不等于明细已采过。

### 11.5 证据不跨查询复用

`safe_fetch()` 每次开始都清零上一轮的 `paths / retry_after_s /
last_block_url / last_block_api / _scene_pending / last_scene`。早退、异常、
SessionBusy 都不会把旧拦截证据当成这一轮的拒绝原因。

响应监听只接受 `document/xhr/fetch`，并排除统计/广告域；图片 403、埋点 503
不再熔断渠道。XHR 被拒时 `last_block_url` 记**页面地址**（人可过验证），
`last_block_api` 另存接口地址（可溯源）。

### 11.6 拦截现场 3.0：200 页面也能留证

人机验证/登录墙经常返回 200 页面。`path_note()` 在确认 `blocked/login`
时补记当前页面 URL，截图仍由采集线程在关上下文前落盘。`去验证` 打开的是
页面而不是 JSON 接口。

### 11.7 并发：先渠道锁，后全局浏览器配额

旧顺序是「全局信号量 → 渠道锁」：两个同渠道等待者会占满全局 2 个浏览器
配额，把其余渠道一起堵死（头阻塞）。现在统一为**先渠道锁、后全局配额**，
探针也按同一顺序。任何线程都不跨渠道持锁，因此不成环。

干预动作全部走 `channel_slot`：手动预热、渠道自检、验证窗口、验证后补采、
网页登录窗口。采集与干预不会再各开一份上下文抢同一 profile。

### 11.8 指纹幂等：采集 / 预热 / 自检 / 验证共用一套身份

`BaseCrawler.fingerprint()` 是唯一来源：

| 面 | 取值 |
|---|---|
| UA / Chrome 主版本 | 真实内核版本（`data/.kernel_major`） |
| 视口 / is_mobile / has_touch | 由该 profile 的 `use_mobile` 决定 |
| locale / timezone | `zh-CN` / `Asia/Shanghai` |
| 出口 | `proxy_map[渠道]` 优先，否则全局 `proxy` |
| canvas 种子 | `crc32(profile_name or name)`，跨重启稳定 |
| stealth | 桌面补 `window.chrome`，移动不补；WebGL 与 UA 形态一致 |

验证窗口**不再强制桌面 UA**：手机 profile 用手机身份过验证。登录窗口默认
同样沿用 profile 身份；只有配置 `crawler.login_desktop: true` 才强制桌面
（手机滑块实在拖不动时的退路，代价是登录/采集指纹不一致）。

### 11.9 可观测 / 可干预 / 可推进 / 可统计 / 可区分 / 可统一

| 要求 | 落点 |
|---|---|
| 可观测 | 节流状态条、`/api/pacing`、`/api/paths`、`/api/trace`、启动/轮末账本日志 |
| 可干预 | 解除熔断、手动预热、渠道自检（可指定国内/国际）、去验证、出口自检 |
| 可推进 | 每轮计划/快/慢/TTL 内、实际未发、熔断次数、会话让位、验证后补采数 |
| 可统计 | 路径/查询/明细/日历四类比率，按渠道×入口×域聚合 |
| 可区分 | PC/H5 × 国内/国际；明细 vs 日历；ip/captcha/login/busy；冷却/陈旧/路径劣化 |
| 可统一 | 单一 `Pacing` 上下文、单一 `channel_slot`、单一 `fingerprint()` 来源 |

## 12. 第四轮：软拒分层、预算可视、临期节奏、路径影子（r380）

这一轮不改采集目标，只把"判错"和"看不见"两块补齐。

### 12.1 软拒是第三类，不是 empty 也不是 blocked

| 信号 | 旧归类 | 新归类 | 正确动作 |
|---|---|---|---|
| HTTP 202 空体 | empty/error | `soft_reject` | 下一轮先预热再查 |

| 干净 200 且无行 | empty | empty | 记真无票 |

strikes**，只置 `needs_warmup`。`note_warmup_ok()` 在**真的拿到风控 cookie** 后

### 12.2 HTTP 状态入账

`path_note(..., http_status=)` 与 `save_fetch_path(..., http_status=)` 已接通，

### 12.3 请求预算可视

"为什么这轮被限流"不再靠猜：是 TTL 挡的、熔断挡的、还是预算等待超限。

### 12.4 临期日期加密

30 天外慢层翻倍（≤1440 分钟）。只调整本键节奏，不改变健康惩罚方向。

### 12.5 路径偏好先跑影子

## 13. 第五轮：干预后一致性（r381）

前四轮解决"少发、发对、判准、看得见"。这一轮只解决一件事：
**干预之后，系统说的和真实发生的必须一致。**

### 13.1 干预成功 ≠ 状态已恢复

| 干预 | 旧行为 | 现行为 |
|---|---|---|
| 渠道自检出数 | 只返回结果，熔断/冷却仍在 | 立刻 `reset` + 刷新该键 TTL |
| 验证后补采出数 | 只落库，渠道仍显示冷却 | 同样 `reset` + 刷新 TTL |
| 手动「解除」 | 直接记 `ok=True` | 立刻单查一次，按**真实结果**落账；未通则重新熔断 |

### 13.2 干预账本（持久化）

新表 `interventions`：`at / platform / action / ok / rows / scope /
before / after / note / ms`。解除、预热、自检、验证各一条，重启不丢
（此前只在内存 `rt["scene"]`，重启即失忆）。`/api/trace` 返回
`interventions`，面板「溯源」按时间倒序列出动作、成败、行数、耗时。

### 13.3 干预前后效果对比

`PriceStorage.intervention_effect(platform)` 以最近一次干预为界，
对比「干预前 24h」与「干预后」的路径成功率，`effect_verdict()` 译成：

- `improved` 干预有效（≥70% 且上升）
- `recovered` 已恢复（≥70%）
- `partial` 有改善但仍偏低
- `no_effect` 未见改善（建议换路径/重登）
- `pending` 干预后还没有新样本（如实说"等下一轮"）

样本不足一律 `None`，不编造百分比。

### 13.4 恢复迟滞与样本护栏（减少抖动误判）

- **连续成功 2 次**才清零 strikes/冷却；单次成功只清"软拒待预热"标记。
  否则"好一轮坏一轮"的渠道会在冷却/恢复间反复横跳。
- 路径劣化判定要求分母里 ≥3 次**非售罄**样本；不足时只降级为
  `degraded`（渠道整体成功率低），不误杀单条路径。

### 13.5 本轮覆盖率（一轮成功率口径）

`last_round.sent_by / ok_by / soft_by` + 顶层 `coverage.ratio` =
有数渠道数 ÷ 实发渠道数。面板显示"本轮覆盖率 67%（有数 携程、途牛 /
实发 五家 · 软拒 去哪儿）"。它与路径账互补：路径账看"哪条路"，
覆盖率看"这一轮到底几家出数"。

### 13.6 成功率杠杆（新增可配置）

| 键 | 默认 | 作用 |
|---|---|---|
| `schedule.near_days` | 3 | 出发 ≤N 天进快层（TTL 减半） |
| `crawler.max_concurrency` | 0（示例 2） | 同轮浏览器并发上限；5 家同秒齐发最像机器人 |
| 查询排序 | — | 按出发日优先，临期先采 |

### 13.7 可干预项补充

面板新增「全部自检」「全部预热」：**顺序执行**（不并发开浏览器），
结果跨自动刷新保留。逐个点 5 家渠道的重复劳动被去掉。

### 13.9 补充：干预后"持续性"与域级归因（同日收口）

- **干预后每 30 分钟趋势**：`intervention_effect()` 额外返回 `trend`
  （bucket / rate / n）与 `regressed`。先好后坏（曾有 ≥70% 窗口、最近
  窗口 <40%）直接判 `regressed`，一致性不成立，建议复查会话/入口。
  - 实现位置（2026-10-27 核对）：`core/storage.py::intervention_effect`，
    分桶 `strftime('%s', ...) / 1800`（30 分钟），**最多 16 个桶**（`trend[:16]`，约 8 小时；r618 起分域切片在取数后做，桶上限由切片截断承担，**不是** SQL 的 `LIMIT 16`）；
    判定 `any(rate>=0.7) and last<0.4`，与上文 70%/40% 一致。
  - 超出 8 小时的回落不会进入 `trend`——时间更早的"先好后坏"要靠 24h 的 before/after 口径判断。
- **样本门槛**：干预后 <3 个样本只报 `provisional`（待复验），
  不宣布"已恢复"；1 次探测成功只能证明"这一刻通了"。

- **域级归因**：路径劣化优先按 `scopes`（国内/国际）判定，提示
  "国际 H5 有效率 0%" 这类精确结论，避免把"国际被登录墙拦住"

`国内 H5 22%` 与 `国际 日历 0%` 两条域级结论。

## 14. 第六轮：异常分类正确性（r382）

真实 24h 账本暴露两处**归因错误**，它们比"限流"更伤成功率：把
"会话没养熟"判成"请重登"，于是白白冷却 15 分钟并让用户去重登。

### 14.1 测到的误判

| 现象 | 次数/24h | 旧归类 | 后果 |
|---|---|---|---|
| 同程 `HTTP 444` / `code=444` | 49 | `login` + `login_suspect=True` | 15 分钟登录冷却、提示重登 |
| 去哪儿"原站无符合条件的航班" | 36 | `login`（被粘滞 `login_suspect` 覆盖） | 同上，且真无票被说成会话失效 |

### 14.2 现在的口径

- **444 / 202 空体** → `soft_reject`：不置 `login_suspect`、不计 strikes、
  不冷却；`needs_warmup=True`，**下一轮自动预热**。
- **710114 / needLogin / 登录页** → `login`：15 分钟冷却 + 提示重登。
- **"无符合条件的航班"** → `empty`：优先于 `login_suspect` 判定，
  不再被上一轮/另一域的会话标记污染。
- `classify_failure()` 里 **soft 优先于 IP 规则短路**：note 里带 444
  字样不会被当成 IP 限流冷却整家渠道。

### 14.3 统一异常词表（可区分）

`FAILURE_KINDS` / `failure_kind(code)` → (中文名, 建议动作, 是否自动自愈)：

| code | 中文名 | 动作 | 自动 |
|---|---|---|---|
| ip | IP/频率限流 | 等冷却/换出口 | 否 |
| captcha | 人机验证 | 同会话去验证 | 否 |
| login | 登录态失效 | 重登 | 否 |
| soft | 会话层软拒 | 下一轮自动预热 | **是** |
| timeout | 请求超时 | 等下一轮/降频 | 是 |
| parse_error | 解析失败 | 排查改版 | 否 |
| empty | 真无票 | 无需处理 | 是 |

### 14.4 复发可跟踪、可溯源

`failure_recurrence(hours, min_count)`：同渠道×入口×状态在 24h 内出现
≥N 次即列出，并附**最近一条现场**（url/http_status/note/rows/时间）。
面板"反复出现"行显示 `同程 日历 会话层软拒×49（自动）· code=444`——
不用再等"连续 3 轮零数据"（可能要 90 分钟）才发现问题。

### 14.5 自愈闭环

`soft_reject` → `needs_warmup` → 下一轮 `_warm_once`（即使不在预热名单）
→ 真拿到风控 cookie 才清标记。全程无需人工；人工只在 `login/captcha`
这类"必须人来"的类目上出现。

### 15.1 用户判断对了：不是无票，是风控

### 15.4 落地

- `TongchengCrawler._intl_window_prices()`：按航线取窗，覆盖
  `[今天+1, +89]`；跨窗日期换锚再取（硬上限 3 次，防死循环）。
- 窗内无价/0 价**不臆造**；渠道 `code=5` 记 `unsupported`（非法航线/
  超窗），网络失败记 `error`，二者都不当"无票"。
- **同轮缓存 30 分钟**（`INTL_WIN_CACHE_S`）：主链路按日期拆多次
  fetch，不缓存会把"每航线 1 次"放大成"每日期 1 次"。实测 12 个日期
  = 2 次请求（第二个窗接 2027-02）。
- 路径账新增 `窗历`（`calendar` + `http=200` + 逐日 date），与旧
  `日历`（签名日历，仍 444）分开记——面板一眼看出"哪条路在出数"。
- 行元素 `source=tc_window_calendar`、`name=日历最低价`、时刻留空、
  **不拆 tax**（窗历只给含税总价）；不是明细就不冒充明细。
- 定时面走窗历（**零浏览器**）：窗历没出数就本轮到此为止，**不落回
  页内日历**（该通路恒 444，落回等于把"每日期 1 次浏览器 + 必失败"
  装回来）。只有探针（人主动要明细）才启浏览器。探针面优先真实明细
  （航班号/时刻），窗历只兜没明细的日期。
- 缓存只填它能覆盖的日期：未覆盖的照常换锚去取（缓存不短路），同一
  锚点不重复打；过期日期在查缓存之前剔除（跨午夜不会被当成有价）。
- 往返：**本通路**取不到往返价（窗历仅单程、页内日历门拒）——记
  `往返/unsupported`，日志只陈述可观测事实，不推断站点自身行为；
  **不拿单程价冒充往返**。

- 面板路径矩阵出现 `窗历` 一行：成功率、明细率 0（诚实的日历族）、

### 15.9 准确性：飞猪国际中转被整类漏采（r386）

**不是限流，是解析器丢行。** 飞猪国际**中转卡片不给航班号**：行头是
`马来西亚亚航长途 等2家航司`（`aria-label=航班号` 的 span 里只有航司
名），后面才是「2程航班」+ 转城市 + 两时刻 + 含税价。旧解析对行头死抠
`^航司 代码$` 正则，判不中就 `continue` —— 一条中转都不进库。

现场取证（同一页面 DOM，登录态）：

| 航线 | DOM 卡片 | 其中中转 | 修复前入库 | 修复后入库 |
|---|---|---|---|---|
| SHA→SIN | 82 | 68 | 14（全是直飞） | **82**（直飞 14 / 中转 68） |
| SHA→LHR | ~150 | ~144 | 6（全是直飞） | **150**（直飞 6 / 中转 144） |

后果是双重的：**条数少**（看着像"渠道没货"）而且**最低价系统性偏高**
——SHA→LHR 飞猪只报直飞 ¥3088，而中转实际 ¥1992，跨渠道比价时飞猪
永远"最贵"。

修法：中转卡片按「航司名（去掉「等N家航司」）+ 转城市 + 起降时刻 +
含税价」如实建行，`code` 留空（渠道不给就不编），`transfer/transCity`
置位；去重键补「航司名+转城市」，否则同一航司同一起飞时刻的不同中转
方案会被压成一条。无行头/无时刻/无价的仍然丢。

准确性交叉验证（SHA→LHR 最便宜中转）：

| 渠道 | 方案 | 含税价 |
|---|---|---|
| 飞猪（修复后） | 海湾航空 经巴林 | ¥1992 |
| 携程 | 经巴林 | ¥1895 |
| 途牛 | 经巴林 | ¥2108 |

同方案、同价格带——补上的是真数据，不是编出来的行。

**连带修复（同一轮发现）：** 补进来的中转行在页面上"看不到"——前端
`srxIsCal` 与后端 6 处 `isCal` 判定都以「有航班号」为前提，飞猪中转卡
片只给航司名，于是 145 条中转被标成日历行：明细率 0、不进直飞/中转
最优池、不参与达标。现已统一为「时刻双空才是日历行」（与
`alerter._is_calendar_row` 同律）。

线上验证（`/api/probe/search` SHA→LHR 2026-11-16，飞猪）：

```

transfer isCal set: [False]      ← 中转是真实班次
direct   isCal set: [False]
海湾航空 16:30 -> 06:35 经 巴林 ¥1992
```

注意两处**有意保留** code 判据的位置：历史行键（`flight_key` / `_srx_flight_key`，无 code
时回退 name）与演示数据播种（演示库无飞猪中转）。它们不是"真实班次"
判定，不应随本修一并放宽。

### 15.10 误判排查：去哪儿国际"只有 60 条"不是漏采（r387）

四条国际航线都恰好 60 条，看着像被硬截断（携程 100–250）。逐层取证：

1. **响应里有分页字段**：`tcount`（78/104/121/133）、`asyncComplete`、
   `asyncInterval`、`nextQtrace` → 确认是流式分页接口。
2. **确实会发多包**：深滚一次抓到 8 个 `touchInterList` 包，每包 60 条，
   第 8 包 `asyncComplete=True`。
3. **但后面的包是重复流**：逐包去重后 `new rows per pack =
   [60, 0, 0, 0, 0, 0, 0, 0]` —— 唯一航班恒为 **60**。
4. **4 轮 × 2 航线复采**：唯一行 60/60/60/60（SIN）、60/60/60/60（LHR），
   而 `tcount` 在 104–133 之间浮动。

**结论：去哪儿国际每轮确实只给 60 个航班身份，我们没有漏数据。**
`tcount` 是渠道更宽口径的计数（含不同价格档/政策组合），不等于"可售
航班身份数"。所以**不按 tcount 去"补行"**——那只会把同班多条政策当
成不同航班，污染唯一性与最低价。

**仍然保留了分页合并**（`_parse_intl_packs`）：渠道若某天真的把超出
60 的**新行**放进后续包，我们会全收（去重保序）；实测当前是 0 新增，
属防御性正确，不改变现状。附日志 `流式分页 N 包 / M 行（渠道 tcount=X）`，
让"是否真的收全"可观察。

### 15.11 准确性复核：跨渠道价差是可解释的（r387）

对 2026-11-16 四条国际航线做跨渠道同班比价复核：

| 口径 | 可比航班 | 价差 p50 | p90 | >60% 异常 |
|---|---|---|---|---|
| 只按「航班号+时刻」 | 330 | 2.7% | 9.1% | **5 个** |
| 再按「舱位大类」分组 | 330 | — | — | **1 个** |

5 个"异常"里 4 个是**舱位不同**被硬比（例：途牛公务舱 ¥3019
vs 携程经济舱 ¥827）。这恰好验证检索台的同班比价指纹 `fp` 已经把
`srxCabinClass(f)` 纳入键——**公务舱和经济舱不会并排比价**，
所以页面上的"可省 ￥X"不会拿公务舱去劝人换渠道。

剩下 1 个（`EY867/EY063` 经济舱 途牛 ¥2840 vs 携程 ¥2551，同税
¥1470、同经停阿布扎比）差 11%，属真实渠道价差；携程该行标注
「无免费行李额」，更便宜与之自洽。早前账上的 ¥5720 是途牛历史报价，
新一轮已自然更新为 ¥2840——不是解析错误。

结论：**当前跨渠道比价链在"同班同舱"口径下是准确的**。无需改动。

### 15.12 误判修正：页脚「扫码下载 App」被当成登录墙（r388）

飞猪国际、携程 H5、同程 H5 的"空结果 → 是否登录"判定都用

### 15.13 静默崩溃：飞猪 H5 回退缺 `os` 导入（r388b）

验证"空结果不再误记登录"时，用非法航线（SHA→ZZZ）打了一次真实抓取，
日志暴露出一个从未被测试覆盖的必崩点：

```
[fliggy][intl] 2026-11-16 列表空/未登录（SHA→ZZZ）
[fliggy] H5 回退异常: name 'os' is not defined
```

`_h5_fallback` 用 `os.path.isfile(h5.session_state_path)` 判断 H5 会话是否
存在，但 `crawlers/fliggy.py` 从未 `import os`。所以**只要 PC 面空/被拦、
走到 H5 兜底，这条路径必然 NameError**——外层 except 只记一行 warning，
整条兜底静默失效，账上只留 `H5 error`。国际航线正是靠这条兜底补数据的。

修复：补 `import os`。真实回归（SHA→ZZZ）：

```
PATH PC   empty | sjipiao.fliggy.com 国际列表
PATH 日历  empty | 日历窗无该日报价
PATH H5:H5 empty | H5 日期选择未匹配     ← 不再 NameError
```

同时加了两条常驻守卫（`tests/test_r388_login_wall_precision.py`）：
1. `fliggy` 必须有 `os` 导入且使用点仍在；
2. **全仓静态扫描**：`crawlers/ core/ main.py webui.py` 不得出现
   「用到但未导入」的 18 个常见 stdlib 名（os/re/time/json/math/…），
   一次覆盖同类静默崩溃。当前扫描 0 命中。

### 15.14 误报修正：陈旧样本不得报「路径劣化」（r388d）

线上复现：去哪儿面板持续提示「国内 API 近 24h 有效率 0%（18 次有效）」。
查账本：API 是**兜底路径**，自 19:00 起就没再被尝试过（H5 一直成功就不
走兜底），18 个样本全是 5–6 小时前的历史 login 行；同域 H5 61.7% 正常。

加新鲜度门槛：`last_at` 超过 **180 分钟**的路径不参与劣化判定（域级与
平台级同时生效；新鲜样本仍照常告警，门槛不吞真问题）。

线上验证（同一份账本；**当时文案快照**，r417 起建议条改称「近 24h 查询成功率」并附退役通路说明）：

### 15.15 失败收敛：图床连续失败熔断（r389）

采集渠道之外的另一个"每轮撞墙"点：GitHub 图床。日志实测每轮都出现

```
[图床] GitHub 上传异常(代理): EOF occurred in violation of protocol (_ssl.c:992)
[走势] GitHub 图库失败，放弃图链路交文本兜底
[总表] 上传失败
```

清零；只作用于 ghimg，不影响 smms/freeimage。

效果：一轮多张图从「每张 2–3 次无谓请求」降到「1 次」，且 10 分钟内
不再重复。文本兜底路径不变，推送内容不缺。

### 15.19 恢复延迟：静默窗结束即补采（r391）

静默窗内跳过轮不落轮次标记，但下一轮仍按 24–37 分钟间隔接力 ——
07:00 窗口结束后最坏再等半小时才有第一轮，此时数据已陈旧 6 小时。

修复链路：
1. `Pacing.seconds_until_quiet_end()`：窗内返回距窗口结束的秒数
   （含跨午夜窗 23:00–07:00；窗外/未配置返回 None）。
2. `sweep()` 在窗口内跳过时写 `rt["_wake_at"]`，日志注明「窗口结束
   N 分钟后自动补采」。
3. `_first_run()` 把该值转交 `sched_state`（一次性键）。
4. `_schedule_next()` 取 `min(常规间隔+抖动, 窗口结束+1 分钟)`。

实测口径：01:30 在窗内 → 剩余 5.5h；06:59 → 60s；07:30 → None；
跨午夜窗 02:00 → 5h。

### 15.21 准确性：渠道不提供舱位时必须标注（r393）

实测（6h 内入库行）：**飞猪 100%（1169/1169）、去哪儿 99%（1298/1305）
的行完全没有舱位字段**，而携程、途牛 100% 有。

先确认这是渠道能力边界而非解析丢失：
- 去哪儿原始报文 `data.flights[].cabinDesc` 本身为空，`binfo` 无舱位键。
- 飞猪列表页 DOM 的 `aria-label` 只有航司/航班号/时刻/机场/时长/价格，
  **没有任何舱位元素**（用户点「选择航班」后在下一页才选舱位）。

风险：明细里舱位片原本只在 `cabinT||cabinCode` 有值时才渲染——舱位缺失
时整段不显示，读者看到 ¥11407 的公务舱行（HO3511）会以为那是经济舱价。
89% 的无舱位行落在常见阈值带内（会被推送/达标判定看到）。

（title 说明"该渠道列表页不提供舱位字段…比价按同班同舱分组时不会与
其他舱位混比"）；日历行不标（避免污染）。三种情况已用真实表达式求值验证：

```
无舱位真班次 → <span class="cmiss">舱位未标</span>
有舱位       → 正常舱位片
日历行       → 不显示（只有"含税"）
```

同班比价不受影响：前端指纹 `fp` 已把 `srxCabinClass(f)`（未知→"未知"）
纳入分组键，无舱位行不会与非经济舱行混比。

**同族补齐：行李额（r393b）**。6h 实测：飞猪 100%（526/526）、途牛
100%（1227/1227）、去哪儿 85%（1103/1305）的行没有行李字段；途牛国际
原始报文里**一个行李相关键都没有**（`bag/luggage/freight` 全零命中）。
明细原本只在筛选命中时才显示托运 kg，缺失时读者无从判断是否含托运。
对真班次补「行李未标」小标（title 明确"不代表无行李，请以渠道详情页
为准"）；有行李或日历行不标。三种情况用真实表达式求值验证通过。

## 16. 第八轮：并发/指纹不变量、账本诚实性与门拒语义（r394–r404）

### 16.1 并发与指纹：从人肉审计转成常驻守卫（r394）

目标里「项目中无并发竞态劣化问题」「采集过程和干预过程浏览器指纹幂等」
两条此前只有人肉审计结论，任何一次改动都可能悄悄破坏。现转为自动化：

| 不变量 | 判据 | 实测 |
|---|---|---|
| 同渠道串行 | 同一平台 4 线程进临界区 | max_concurrent == 1 |
| 跨渠道有界 | 4 个平台并发 | max_concurrent <= CHANNEL_GATE 容量（2） |
| 锁序固定 | 源码钉 `channel_slot` | 先渠道锁、后全局配额 |
| 指纹单源 | 连续两次 `fingerprint()` | 完全相同，9 个固定键 |
| 切换必还原 | AST 配对 `use_mobile = False` / `finally: = bak` | 6 处全成对 |

锁序为什么必须钉：反序（先握全局配额再等自家渠道锁）会头阻塞——两家
各自握着配额等锁，其余渠道全被挡在配额之外，等于把并发上限从 2 降到 1。
`browser()` 不取 CHANNEL_GATE，`_probe_plat_lock` 与 `channel_slot` 同序，
所以没有重入死锁，也没有旁路。

指纹为什么要钉 `use_mobile` 还原：各渠道为了国际/PC 场景会临时切
`use_mobile = False`（桌面 UA/视口），漏还原就会让下一次采集带着上一
场景的身份——风控视角是同一会话里设备特征跳变，等同于会话被接管。

守卫写法踩的坑（记下来免得重犯）：第一版用 1600 字字符窗口找配对的
`finally`，子句一长就误报 3 处；第二版改成「向上找包住赋值的 try」，
方向又反了（切换写在 `try` 之前），6 处全误报。正确形态是**向下找最近
的一个 try**，且中间不得再出现别的 `use_mobile` 赋值。守卫自身也有用例
（`test_toggle_guard_catches_missing_restore`），避免测试变成哑的。

### 16.2 通路改名让「已恢复」永久失联（r395）

**症状**：实时库 24h 复发账里，同程国际 SHA→BKK/LHR/NRT/SIN 四条线各挂
12–15 次 `soft_reject`，`recovered=false`，界面因此一直显示「需人工」。
但同一批航线的窗历行**每轮都在出价**（`path_status=calendar, rows=1`）。

**根因**：r384 把同程国际通路从「日历」换成「窗历」——同一业务通路的
新入口名（单次 HTTP/航线、只出含税总价）。而复发账的恢复判定按
`entry_path` **字面精确匹配**成功行：

```
旧「日历」的失败行 → 找不到 entry_path='日历' 的成功行 → 永远需人工
新「窗历」的成功行 → 与旧失败组完全无关
```

换名当刻旧账就与新成功失联，且**永远不会自愈**——这是最坏的一类状态
谎报：把一个已经好了的问题永久说成需要人工介入，用户会反复去重登、
去查自己根本不存在的问题。

**修法**：日历族 `CAL_PATH_FAMILY = ("日历", "窗历")` 按族匹配恢复。
族内认的是通路语义（只出价、不证明细），不是渠道；族外仍按字面入口名，
**不让 H5 的成功去顶日历的账**（不同通路不互相担保）。族表放在
`core/models.py` 单点定义，`pacing`（族抑制）与 `storage`（恢复判定）
共用，避免两处各写一份后漂移。

**验证**（真实库，同一份数据前后对比）：

```
修复前： tongcheng 日历 SHA→BKK  soft_reject×15  recovered=false
修复后： tongcheng 日历 SHA→BKK  soft_reject×15  recovered=true
        （last_ok_at=2026-10-27 07:01:02，来自窗历行）
```

四线全转 `true`；其余 18 个分组不变（无副作用）。守卫用例覆盖四种形态：
改名后算恢复、族外不跨通路担保、窗历自己失败时不谎称恢复、别的航线
成功不顶本航线。已确认这些用例在旧代码上会红（`test_rename_counts_as_recovered`
报 `assert False is True`），不是哑测试。

**教训**：任何「按入口名/路径名做账」的统计，都要能承受**通路改名**。
改名事件本身是对的（新通路确实更好），坏的是账本把名字当成了身份。
做这类判定时先问一句：这条通路将来会不会改名？会的话，账本就得按
语义分组，而不是按字面。

### 16.3 归类改写后没有重新聚合，面板并列两条同名行（r395b）

**症状**：面板「反复出现」区出现两条一模一样的行——
`去哪儿 API 空结果×4 · 原站返回无符合条件的航班…` 与
`去哪儿 API 空结果×3 · 原站返回无符合条件的航班…`。

**根因**：口徑改写发生在 SQL 分组**之后**。这两个数其实是同一件事在
库里分成两组：`path_status='login'` 的 4 条与 `'empty'` 的 3 条。改写
规则把前者也判成 empty，两组的 `status` 就撞成了同一个值，但分组早已
在 SQL 里做完，输出便并排两条。

**修法**：改写完成后按（渠道×入口×航线×状态）再合并一次：计数相加、
首末时间取极值、证据取较新那条。实测 22 组 → 14 组，`4+3=7` 正确相加，
其余组不受影响。

**为什么不干脆把改写下推到 SQL**：改写要读 `note` 里的自然语言关键词
（444/非法链接/202/无符合条件的航班/1999），在 SQL 里写等于把业务口径
塞进 LIKE 表达式，后续每加一条改写规则都要动 SQL。放在 Python 里做、
之后重新聚合，规则和结构各自清晰。

**教训**：凡是「先按 A 分组、再把 A 改写成 B」的流水线，改写后必须
重新聚合一次，否则分组键的旧值会以另一种形式泄漏到输出（这里是同状态
两组并列）。守卫用例同时钉了两个方向：该合并的合并
（`test_relabel_groups_merge_after_classification`）、不该揉的不能揉
（`test_relabel_merge_keeps_distinct_statuses_apart`）。

### 16.4 指纹幂等的真正含义：跨实例一致（r394b）

`test_fingerprint_is_single_source_and_stable` 只证明了**同一实例**二次取值
相同——那太容易满足（返回一个常量字典即可），却防不住真正会出事的形态：
**进程重启后新实例换了设备特征**。对风控而言那是"同一账号换机登录"。

实测跨实例：两个 `QunarCrawler({}, logger)` 的 `fingerprint()` 逐键相同
（ua=iPhone／viewport 390×844／zh-CN／Asia_Shanghai／is_mobile／has_touch／
proxy 空／stealth／seed=200）；携程同样成立。已加
`test_fingerprint_is_identical_across_instances` 常驻守卫。

当前实现是**固定值**（不是随机池），所以幂等性来自"没有随机源"，而不是
来自种子稳定。若将来引入多 UA 轮换，必须保证「同渠道 × 同账号」的选取
是确定性的（按账号/渠道哈希取模），否则本守卫会立刻变红——这正是它
存在的价值。

### 16.5 溯源断在最后一厘米：request_url 从未被写入（r396）

**症状**：`fetch_paths` 有 `request_url` 列，`failure_recurrence` 一直在
`SELECT request_url` 并把它当证据回显——但真实库 601 行里**全为空**
（0/601）。也就是说「这条路径失败时打的是哪个地址」这一栏永远是空的。

后果不是"少一个字段"，而是**可溯源/可验证/可复现同时失效**：事后只能
翻 debug 截图去猜入口，无法按 URL 复盘是哪条入口、哪个 query、哪个日期
被拦，也无法验证"换个入口是否就好了"。

**根因**：`path_note` 在 blocked/login/soft_reject 时**已经算出了页面 URL**
（用来填 `last_block_url` 和现场截图），但只写进了实例变量，没写回
`rec`；三个持久化点（主采/补采/自检）也都没给 `save_fetch_path` 传
`request_url`。整条链路上没有任何一处把 URL 送到列里。

**修法**（三层，缺一层就会留半吊子溯源）：

1. `path_note(..., url="")` 新增显式参数：调用方传**自己真实使用的**
   URL，保存为 `rec["url"]`。
2. 被拦状态仍用页面 URL 兜底（原有行为），但**不覆盖**调用方显式值——
   同一轮里 H5 浏览器失败后接 httpx，页面早已关闭，拿 `_last_page` 当
   URL 会把 A 路径的地址记到 B 路径头上，那比空值更糟。
3. 主采/补采/自检三个落账点全部 `request_url=rec.get("url")`。

已接线：qunar H5（`URL_TPL` 真实列表页）与 API（`touchInnerList`）显式
给值；其余渠道的被拦/登录/软拒走第 2 层页面兜底——那正是运营最需要
"点开看一眼"的形态。

守卫 `test_r396_request_url_traceability.py` 五条：显式值保留、显式值
压过页面兜底、无值时页面兜底仍生效、端到端写进列、三个落账点一个都
不许漏（漏一处会出现"有些路径有 URL、有些没有"，比全无更难排查）。

### 16.7 登录墙被算成「错误」，把"该重登"说成"该重试"（r397）

**症状**：`path_stats` 对同程 24h 报 `error=53`、渠道错误率 40%，看起来
像链路坏了。查账本：这 53 条 **全部是 `path_status='login'`**（444 历史
行），真正的网络/解析/超时错误是 **0**。

**根因**：`bump()` 的分类是 if/elif 链，blocked / soft_reject / empty /
unsupported 各有专桶，`login` 落到最后的 `else: error`。于是：

- 渠道错误率虚高（同程 40%），读者以为要排查链路；
- 处置方向被带偏：error 的语义是"重试/看现场"，login 的语义是"重登"。
  按 error 处置＝让人反复重试一个**只有重登能解**的状态——这正是目标里
  「异常可分类」「可解决」的反面。

**修法**：加 `login` 专桶（node 与 path 两级都建；`bump` 里在
unsupported 之后、else 之前判 login）。login 仍算失败（不进
`rate_excl_empty` 的分母剔除），只是不再冒充 error。

**验证**（真实库，同一份数据）：

```
修前： tongcheng attempts=132 ok=73 error=53 soft=6
修后： tongcheng attempts=132 ok=73 login=53 error=0 soft=6
```

**分类桶现在的完整语义**（六桶一状态，互不代偿）：

| 桶 | 含义 | 处置 |
|---|---|---|
| ok / calendar | 出数（明细 / 只出价） | 无需操作 |
| empty | 明确无符合条件的航班 | 无需操作（真无票） |
| unsupported | 能力边界（往返无源/超窗） | 无需操作 |
| soft | 444/202 门拒 | 预热，会自动恢复 |
| login | 真登录墙 | 重登（人工） |
| error | 网络/解析/超时 | 重试/看现场 |

守卫 `test_r397_login_not_error.py` 四条，其中
`test_buckets_sum_to_attempts` 钉住"六桶必须加总回 attempts"——防止将来
新增状态时又落进某个万能桶、在统计里凭空消失。已确认前两条在旧代码上
会红。

### 16.8 「无票」证据跨界污染：跨日期、跨路径（r398）

`_last_no_result` 是 qunar 用来区分「站点明确说没票」（empty，无需操作）
与「登录墙/解析失败」（login/error，要处置）的开关。它在两处越界：

**(a) 跨日期**：只在 `fetch()` 开头清一次，循环日期时不清。上一日期确认
无票后，本日期**任何**无名失败都会被染成 empty——一个真登录墙被说成
无票，用户以为今天真没航班。

**(b) 跨路径**：httpx（API）路径不认自己响应里的措辞，也不在自己发
请求前清标志。实测库里有 18 行 `API/login` 却写着「原站返回无符合条件
的航班」——那是 H5 的判定漏到了 API 头上。

**修法**：`_fetch_one` 里 H5 与 API 各自在发请求前 `_last_no_result=False`
（每天每路径独立取证）。

**为什么值得较真**：empty 与 login 是处置方向相反的两端——empty 正确时
用户什么都不用做，login 正确时用户必须重登。任何一端误判都会把人推向
错误动作；而它们的证据来自**不同的请求**，本来就不该共享。

守卫 `test_r398_qunar_evidence_scope.py`：跨日期不泄漏、API 起点不继承
H5 判定、真无票仍 empty。第 1、4 条已确认在旧代码上会红。

### 16.8b 修正：httpx 的 1999「没有航班」是门拒文案，**不是**真无票（r398b）

上一节我最初把 httpx 的 `1999 + 没有查询到符合条件的航班` 判成 empty
（"真无票"）。**这个结论是错的**，实测把它推翻了：

同一 token、同一天、连续打了四条**已知有票**的航线：

| 航线 | 别处实测是否有票 | httpx 回应 |
|---|---|---|
| SHA→BKK 2026-11-16 | 有，窗历/浏览器 ¥662（9C7293） | code=-1 + 同文案 + data=null |
| SHA→HAK 2027-01-29 | 有 | 一字不差同文案 |
| HAK→SHA 2027-02-14 | 有 | 一字不差同文案 |
| SHA→NRT 2026-11-16 | 有 | 一字不差同文案 |

真无票不会**恰好四条全无**，更不会与我们在别处刚采到的价矛盾。这是
token 直连形态被整体门拒，那句文案只是门拒的固定话术。

**所以三种记法里只有一种是对的**：

```
empty        → 谎报"真无票"，与已采到的 ¥662 自相矛盾   ✗
login        → 催人重登一个 H5 明明在出数的会话          ✗
soft_reject  → 门拒、预热可解，事实如此                 ✓
```

改为在 `_fetch_via_httpx` 命中该文案时置 `last_soft_reject =
{"kind":"token_gate"}`，`_fetch_one` 把 API 记成 `soft_reject`，note 写
「httpx 直连整体门拒（1999 文案不可信）」。

**教训**：同一句文案在不同通路上含义可以完全不同。H5 弹「没有航班」
是真的查了没票；token 直连弹同一句，是根本没让查。判断一个信号的含义，
必须**跨样本对照**（换航线还一样吗？和别处采到的价矛盾吗？），不能只看
这句话本身说了什么。这也是「宁缺勿错」在状态分类上的落地：不确定时记
门拒（可自愈、不催人），不记 empty（会让人以为真的没票而不再关注）。


### 16.9 同程窗历是城市级最低价，不是该机场的票价（r399）

r384 上线窗历后，同程国际每轮出数。但行是按**配置的机场码**落库的，
而窗历接口按机场码去查，回的是**城市**最低价。实证（真实接口，同日）：

```
SHA→LHR  n=90  10-27=2492  10-28=2507  10-29=2545  10-30=4041
SHA→LGW  n=90  10-27=2492  10-28=2507  10-29=2545  10-30=4041   ← 逐日同价
SHA→NRT  n=90  10-27=1624  10-28=1412  10-29=1292  10-30=1307
SHA→HND  n=90  10-27=1624  10-28=1412  10-29=1292  10-30=1307   ← 逐日同价
```

同一城市的两个机场返回完全一致的序列，说明它给的是城市最低价。

**风险**：关注 SHA→LHR 的人看到「¥2492」会理解成希思罗的票价，而它可能
落在盖特威克（差一趟跨城交通）；NRT/HND 同理。这不是价格算错，是**口径
没标注**——读者会按自己脑中的口径去理解。

**修法**：行仍按配置的机场码落库（用户按机场关注，不能改主键语义），
但元素里带 `cityLevel` 戳：机场码 ≠ 渠道城市码时为 true。单机场城市
（BKK/SIN）为 false，不误标。

**为什么不改成按城市码存**：那会让「SHA→NRT」的监控记录突然变成
「SHA→TYO」，破坏用户已有的关注/告警/历史的对应关系；且用户确实关心
具体机场。标注口径比改变口径更安全。

守卫 `test_r399_tc_city_level.py` 四条：多机场城市必标、伦敦必标、
单机场城市不误标、标注不破坏原有溯源字段。

**同类待查**：其余渠道的国际日历（携程/飞猪）是否也有城市级归并，
尚未逐家实证——按"宁缺勿错"，没有实测前不假设。

**待查项已核查（携程）**：有同行担心"其他渠道国际日历是否也城市级归并"。
查 48h 真实库：携程国际日历行只有 **1 条**（`SHA→BKK`，无 `source` 字段，
`code=''` + 无时刻），其余国际行全是带航班号的真实明细。也就是说携程
国际基本不走日历兜底，城市级口径对它没有实际影响面，故不加 `cityLevel`
戳（宁缺勿错：没实测到差异就不加标注，避免制造假信号）。

若将来携程国际日历行变多且涉及多机场城市（LON/TYO/NYC），再按同程
同样方式实测 LHR/LGW 是否同价后补标注——**先测再标**。

### 16.10 「当前搜索无航线」是通道级门拒，不是真没航班（r400）

**症状**：qunar 有些查询每轮都 0 行，账本记 `empty`（真无票），面板据此
判定"今天确实没航班"，用户自然停止关注。

**实测**（2026-10-27 08:0x，同一会话连打四条，浏览器与 httpx 各一遍）：

| 航线 | 别处是否有票 | 回应 |
|---|---|---|
| SHA→BKK | **有**，2 小时前同渠道采到 ¥662（9C7293） | `ret:false code:3`「当前搜索无航线，请更换城市重新搜索」 |
| SHA→HKG | —（换「香港」「中国香港」两种名都一样） | 一字不差同上 |
| SHA→NRT | 有（窗历/别渠道） | 一字不差同上 |
| SHA→TYO | 同上 | 一字不差同上 |

四条回应**一字不差**，且与实际有票的事实矛盾 ⇒ 这是通道级门拒，
`code:3` 只是门拒话术，跟"这条航线有没有航班"无关。

**为什么不能记 empty**：`empty` 的语义是"站点明确说没票，无需操作"。
一旦这么记，读者会相信真没票而停止关注——把一次可以被预热救回的拦截，
变成了一条永久沉默的航线。这正是「宁缺勿错」要避免的方向。

**修法**：`_blanket_gate_text()` 识别 `code==3 + "无航线"`，浏览器与
httpx 两条路径都先判门拒（早于 no_result 判定），记
`soft_reject` + 原文案；证据逐路径复位，不跨路径泄漏。

顺带修同族的一处：H5 **完全没拿到东西**（无响应、空正文、无任何风控/
无票证据）此前也落 `empty`。改为 `error`——"没有证据"不能用来支撑
"无票"这个结论，应记成基础设施层没拿到、去看现场。

**三次同类模式的总结**（r398b / r400）：同一个"没有航班"的说法，
在三条不同通路上含义各不相同——

| 通路 | 文案 | 真实含义 | 正确记法 |
|---|---|---|---|
| H5 弹窗（1999 + 明确措辞） | 没有查询到符合条件的航班 | 真查了，没票 | `empty` |
| httpx token 直连（1999） | 同上 | 根本没让查（整体门拒） | `soft_reject` |
| H5/httpx（code 3） | 当前搜索无航线 | 通道级门拒 | `soft_reject` |

判别方法固定为**跨样本对照**：换航线还一样吗？与别处刚采到的价矛盾吗？
一样且矛盾 ⇒ 是门拒，不是航线属性。守卫
`test_r400_qunar_blanket_gate.py` 六条，其中三条专门钉"门拒 ≠ 无票"。

### 16.11 有行无价：`min(prices)` 空序列把异常留成了无证据的空（r401）

**症状**：2026-10-27 09:30 两条 SHA→HAK 的账本自相矛盾——

```
09:30:10 SHA→HAK 2027-01-29 H5   empty  「原站返回无符合条件的航班」
09:30:10 SHA→HAK 2027-01-29 API  ok     「原站返回无符合条件的航班」 rows=0
```

`ok` 却 `rows=0`、`note` 又写着无票，三者互斥。而同一天 08:48 与 10:08
同航线都拿到 70+ 行，说明这条航线有票。

**根因**：httpx 解析出明细行、但**没有任何一条带价格**时：

```python
prices = sorted({f["price"] for f in flights if f.get("price")})
return float(min(prices)), flights      # min(()) → ValueError
```

`ValueError: min() arg is an empty sequence` 穿过 `_fetch_one` 抛到外层，
被兜底逻辑记成一次**不带证据**的失败；上层再叠上"无票"话术，就成了
上面那三条互斥的记录。浏览器路径早就有 `if prices:` 守卫，httpx 这条没有。

**修法**：httpx 同样在 `min()` 前判空，命中时置
`last_soft_reject={"kind":"no_price"}`，note 写"解析出 N 行但均无价格"——
把"有行无价"这个事实如实写出来，不再伪装成无票。

**教训**：`min()`/`max()`/下标 `[0]` 这类"必然非空"的假设，正是把
**可解释的失败**变成**不可解释的失败**的地方。异常一旦穿过记账层，
在账本里留下的往往不是"崩溃"，而是一条看起来正常、实则无证据的记录——
比直接报错更难查。守卫 `test_priceless_rows_do_not_crash`
与 `test_ok_status_always_has_rows`（ok 必须 rows>0）已落地，前者
在修复前会红（`ValueError: min() arg is an empty sequence`）。

### 16.12 携程国际：「没拿到 / 没解析出」被记成「真无票」（r402）

**症状**：2026-10-26 13:47 一条记录：

```
ctrip PC SHA→BKK 2026-11-16  empty  「国际列表未解析到航班」
```

而同一航线同一日期在 10-27 10:03 采到 **221 行**。这条 `empty` 两头都不
成立：一是有票，二是 note 自己写着"未解析到"——**它自己都说不清是没票**。

**根因**：`_fetch_intl` 的两个失败分支都落 `empty`：

| 分支 | 事实 | 旧记法 | 问题 |
|---|---|---|---|
| 一包响应都没到 | 本机/链路没拿到东西 | `empty` | 与"站点说没票"无关 |
| 收到包但解析不出航班 | 可能改版打穿选择器 | `empty` | 解析失败 ≠ 无票 |

**修法**：两个分支都改 `error`（`blocked` / `login` 仍优先）。
`empty` 从此只用于"站点明确说没票"的形态——目前携程国际没有这种分支，
所以这里不再出现 `empty`。

**范围克制**：飞猪 / 途牛 / 同程 72h 内 `empty` 记录均为 **0**，没有观察
到同类误标，本次不动它们（没实测到就不改，避免制造新风险）。

**这是同一个病的第四次出现**（r398b / r400 / r401 / r402），病名是
「**用"没证据"去支撑一个肯定性结论**」。四次的具体形态各不相同：

```
r398b  httpx 1999「没有航班」      → 是门拒文案，不是无票
r400   code=3「当前搜索无航线」     → 是通道级门拒
r401   有行无价 → min() 抛异常      → 留下互斥的 ok/rows=0/无票note
r402   「请求无响应」「未解析到」   → 是没拿到/解析失败，不是无票
```

判断口径固定一条：**这个状态值要不要让用户"什么都不做"？** 要，才配
`empty`；只要有疑问，就记 `error`/`soft_reject`（可查、可重试、可自愈），
绝不用一个漂亮的"无票"把问题盖住。

### 16.13 把判据固化成跨渠道守卫，又抓出三处（r403）

前四次（r398b/r400/r401/r402）都是**逐个发现、逐个修**。这次把判据
写成结构化守卫，横扫全部渠道源码，一次抓出**三处**同类：

| 位置 | 旧记法 | 文案 | 改为 |
|---|---|---|---|
| qunar 国内 H5 末位兜底 | `else "empty"` | （无任何证据） | `error` |
| qunar 国际 H5 | `empty` | 「国际列表有响应但未解析出价格」 | `error` |
| tuniu H5/API | `empty` | 「接口有响应但未解析出价格」 | `error` |
| tongcheng H5列表 | `empty` | 「同程国际 H5 未解析到航班」 | `error` |

守卫 `test_r403_empty_needs_evidence.py` 四条：

1. **伪 empty 措辞扫描**：「请求无响应 / 未解析到 / 没拿到 / 无证据」
   不得出现在写了 `empty` 的代码附近（只看代码行，跳过注释）；
2. **每个渠道都要有 error 出口**：没有 `"error"` 字样的渠道说明失败时
   只能二选一（login/empty），迟早会把别的东西塞进 empty；
3. **empty 不得写在裸 `else` 上**：`else "empty"` 这种形态一律视为
   "其他全失败就当成没票"，是这类 bug 的共同写法；
4. **六桶齐全**：path_stats 必须同时有 ok/empty/login/blocked/soft/
   unsupported/error（r397 的分离不能回退）。

守卫自身的坑：第一版把注释也算了进去，把我解释规则的那行注释误报成
违规。改成"先按 `#` 切掉注释再判断"后，剩下的三处全是真问题——守卫
必须先证明自己不会误报，否则会被后来的人关掉。

**这条判据值得单独记下**：

> `empty` 的代价是"用户从此不再看这条航线"。所以只有**站点明确说没票**
> 才配用它；其余一律 error/soft_reject——宁可让人多看一眼现场，也不能
> 用漂亮的"无票"把问题盖住。

### 16.14 门拒还会误触发退避与「会话失效」（r404）

r400 把 `code:3 当前搜索无航线` 识别成门拒并记 `soft_reject`，但**只改了
记账，没改重试链**。于是同一次门拒还会走完 r385 之前的退避逻辑：

```
back = self._BACKOFF_S[attempt]          # 90 / 180 / 300
...
QunarCrawler.login_suspect = True        # ← 把会话判成失效
```

两个后果：

1. **白打请求**：确认门拒（四条航线一字不差同文案）后在 90s 再打一遍，
   注定同果。守卫实测：旧代码跑完这条用例要 **188 秒**，新代码 0.0 秒、
   `inner_calls=1`。
2. **误导用户重登**：置 `login_suspect` 会让界面显示「会话失效，建议重登」，
   把用户推去重登一个完好的会话——正是 r397 要分的"该重登 / 该重试"。

**修法**：退避分支前先看 `last_soft_reject.kind == "blanket_gate"`，命中即
`return []`——不在同轮退避、不置 `login_suspect`。普通无名空结果仍按原
逻辑退避一次（`test_ordinary_empty_still_retries` 钉住，防修过头）。

**教训**：识别出一个新状态，只改"记账"是不够的——控制流里凡是
`if 失败: 退避/置标志` 的地方，都要问一句"这个失败是新的那类吗"。
账本说对了、动作还错着，用户看到的仍是错的动作。

### 16.15 守卫自己也会漏：字面标记 → 正则，又抓两处（r405）

r403 的守卫用**字面短语**匹配（「请求无响应」「未解析到」……）。它漏掉
了 `fliggy_h5.py`，因为那里的文案是：

```
"H5 无 listingsearch 响应"
```

——中间夹了个单词，字面短语匹配不到。改成正则（`无.{0,24}响应` /
`未(解析|拿到|获取)` / `没有(拿到|收到|获取)`）后，一次又抓出两处：

| 位置 | 文案 | 实情 | 处置 |
|---|---|---|---|
| `fliggy_h5.py` | H5 无 listingsearch 响应 | **连响应都没等到** | 状态 `empty`→`error` |
| `tongcheng.py` 日历 | 国际日历未拿到该日报价 | 渠道**回了**、该日无报价 | 状态保留 `empty`，**文案**改为「渠道日历该日无报价」 |

这两处值得并列看，因为它们方向相反：

- 前者是**状态错**（没拿到却记成没票）→ 改状态；
- 后者是**文案错**（真无票却写成"没拿到"）→ 改文案。

同一句"未拿到"，一处是实情、一处是措辞问题——所以修的时候要分清是
**状态说谎**还是**说明书说谎**。

**教训**：守卫跑绿只说明"没被它抓到"，不说明"没有问题"。第一版守卫 4/4
全绿，实际漏了一个文件；只有把匹配放宽（并保留"不生误报"的自检）才
把漏洞补上。守卫的覆盖面本身也要被审视——**关键词表就是它的盲区边界**。

### 16.16 退役的通路还在拖低渠道健康度（r406）

**症状**：24h 查询级成功率——携程/飞猪/途牛 100%、去哪儿 94.6%，
**同程只有 63.5%**。看起来同程病得最重。

拆开看：

| 通路 | 24h 查询 | 有数 | 成功率 | 最后尝试 |
|---|---|---|---|---|
| 窗历 | 54 | 54 | **100%** | 12:19（在跑） |
| H5 | 7 | 7 | **100%** | 08:16 |
| 日历 | 35 | 0 | **0%** | 10-26 22:36（已无人再试） |

「日历」是 r384 之前的老通路，已被「窗历」取代，且**最后一次尝试停在
10-26 22:36**——之后系统再没试过它。但它仍落在 24h 窗口内，35 次必败
查询把一条其实每条都成功的渠道算成了三分之二坏。

只看窗历上线后（05:30 起）：21 次查询、21 次有数、**100%**。

**修法**：`path_stats` 增加「在用口径」`query_rate_live` / `query_attempts_live`
与 `retired_paths`，原口径保留可对照。判据只用时间先后与产出，不猜语义：

```
路径 P 已淘汰 ⇔ ① 窗口内一次都没成功
              ② 存在另一条路 Q，Q 的最后尝试晚于 P
              ③ Q 在窗口内有过成功（确实接住了活）
```

**① 是必须的**——第一版漏了它，把**携程 PC（24h 成功 129 次）**判成退役，
只因为它最近一次尝试比 H5 早几分钟。守卫
`test_live_path_with_success_is_never_retired` 就是钉这次误判的。

**"更晚的纯旧路径尝试"会让退役判定失效**（此时旧路径自己是最后尝试者，
无法证明被取代）——这是有意的保守：宁可少判退役，也不要把"还在试的路"
说成废弃。逆向保护同样成立：失败路径若没有"更晚且成功"的替代者，不进
名单（可能只是被限流，不是被替换）。

实测效果：同程 63.5% → **100%**（q_live=61），其余四家不变；携程 PC
不再被误判（retired 为空）。

**为什么不直接删掉旧「日历」的账**：历史数据是"这条通路当时确实这样"
的事实，删了就失去了"什么时候换的路、换之前坏了多久"的追溯。正确做法
是**分口径呈现**，而不是篡改历史。

### 16.17 成功路径也在留地址了，且必须是"真的那个"（r407）

r396 补 URL 时只覆盖了被拦/登录/软拒（走页面兜底）。出数时 `request_url`
仍然恒为空——真实库最近一条窗历成功记录：

```
entry_path=窗历  path_status=calendar  rows=1  request_url=（空）
```

于是"这条成功记录当时打的是哪个端点、哪些参数"无法回答，复现与对照断了。

**修法**：给同程两条成功路径补地址——

| 路径 | 记的地址 |
|---|---|
| 窗历 | `special._TC_CAL_URL` = `wx.17u.cn/cheapflights/bffapi/cheapflightapi/lowestprice/queryCalendarLowestPrice` |
| H5列表 | 页面实际 URL（`page.url`） |

**容易踩的坑**：同程文件里有两个"日历"地址——

- `INTL_CALENDAR_API` = `www.ly.com/miflightapi/ts/calendar`：**已被签名
  门拒，恒 444**（r384 定案）；
- `_TC_CAL_URL` = `wx.17u.cn/...queryCalendarLowestPrice`：现在真正在用的。

顺手记错的话，排查的人会拿着一个"根本不会成功"的地址去复现成功记录，
比不记更浪费时间。守卫 `test_recorded_url_is_the_one_actually_called` 专门断言：
窗历那条 `path_note` **前后 1100 字符的代码块内**不得出现 `INTL_CALENDAR_API`
（只看代码行、跳过注释）。

> 注意范围：这是**局部守卫**，不是全文件禁令。`crawlers/tongcheng.py` 里
> `INTL_CALENDAR_API` 仍作为常量定义与旧路径构造函数存在（3 处），那是合法的；
> 被禁的只是「把已停用的地址写进成功记录的 path_note」。

**"可溯源"的完整定义**：不是"失败时能查"，而是**每一条账都能回答
"这次请求到底发了什么"**。只覆盖失败等于只覆盖了一半。

### 16.18 同一次查询并列两条互斥结论（r408）

**症状**：真实账本同一次查询（同一 `attempt_id`、同一秒）：

```
#635 H5 soft_reject  「1999/8 间歇放行（单次，免登录冷却）」
#636 H5 login        「1999/8 连续 2 次未放行（疑会话失效）」
```

一条说"单次、不用管"，下一条说"连续 2 次、请重登"。用户读到时无法
判断该信哪条，回溯时也说不清当时到底失败了几次。

**根因**：r385 的分层是"先按当时计数写一条"。同轮内先写了
`soft_reject`，随后计数升到 2、升级分支又写一条 `login`，**没有撤掉
前一条**。

**修法**：升级分支写 `login` 之后，把本轮同日的那条 `soft_reject` 从
`self.paths` 剔除（只删本轮同日的，不碰历史与其他日期）。

**为什么不能留着两条**："先软后硬"在代码里是真实的过程，但在**账本**
里它们是同一件事的两个阶段，并列展示等于把过程当成了结论。账本要的是
"最终判定"，过程该进日志（已经进了）。

**教训**：这类"状态升级"很容易只写不加删。凡是 `if 条件变化: 再记一条`
的地方，都要问"那前一条还算数吗"。同样的形态在 r395（归类改写后同名
并列）已经出现过一次——**账本里同一个键只能有一个结论**。

### 16.19 把「账本必须满足什么」写成常驻不变式（r411）

r394–r410 修的全是同一类病：**账本说了不该说的话**。逐 bug 修是必要的，
但修完还得让"下次再犯就立刻红"。于是把不变式固化：

| 不变式 | 判据 | 反例（本轮修过的） |
|---|---|---|
| 成功必有数据 | `ok`/`calendar` 的记账点必须带 `rows=` | r401 `ok + rows=0` |
| 失败必无数据 | 非 ok 状态不得 `rows>0` | — |
| 一次查询一条账 | 同 `attempt×路径` 不超过 2 条 | r408 并列互斥两条 |
| empty 必须是真无票 | empty 的 detail 不得含「未解析/无响应/没拿到」 | r398b/r400/r401/r402/r403/r405 |

前两条在源码层扫（`path_note("…","ok"` 后面 220 字符内必须有 `rows=`；
`empty` 后面不得出现失败措辞，且**跳过注释**——解释规则本身的注释会被
误报，这是 r403 就踩过的坑）。后两条查运行期库（只看最近 2 小时，历史
数据不追究：修复前的痕迹是事实，不该为此改库）。

**负控已验证**：把途牛的 detail 改成「未解析出价格」，守卫立刻变红；
改回即绿。不做负控的守卫等于没写。

**这条经验值得单独记**：与其每轮重新"找 bug"，不如让**不变式替我们找**。
本轮 6 个提交（r398b–r405）里有 5 个是守卫发现的，不是人一眼看出来的。

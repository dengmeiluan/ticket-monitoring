## 开启 App 渠道（三步）

> 面向"我想用 App 渠道，但不知道从哪一步开始"。**每一步都能直接粘命令。**

### 第 1 步 · 环境自检并自动补齐

```bash
python -m core.setup_check --fix
```

它会做：装依赖 → 装 chromium 内核 → 建 `config.yaml`/数据目录 → **尝试重启模拟器并等 adb 就绪**。
最后一行结论必须是 `可以开跑`；只要还有 `⚠/✗`，先按它那行后面的 `→` 处理。

关键看两行：

| 行 | 想要的结果 | 没有的话 |
|---|---|---|
| `App 通路` | `已连到设备（127.0.0.1:16384）` | 见下面「adb 连不上的四个卡点」 |
| `配置` | 不再点名 `未订阅 app_*` | 走第 3 步 |

### 第 2 步 · 装 App、写配置、等伪装生效

```bash
# 装好后重启实例并等待伪装生效（10 分钟左右，别中断）
python scripts/setup_device.py --apply --reboot --enable-app-channels
```

- 自动发现 MuMu 就够用；装在非常规目录时加 `--mumu "D:\Program Files\Netease\MuMuPlayer-12.0"`（目录或 `MuMuManager.exe` 都行）；
- 多开实例不是 0 号时加 `--vm 1`；
- adb 非默认端口时加 `--adb <adb.exe 全路径> --serial 127.0.0.1:<端口>`；
- 只想体检不改设备：去掉 `--apply`（默认就是只读体检）。

`--enable-app-channels` 会把可用的 App 渠道写进 `users[].platforms` 并打开 `android.enabled`。

### 第 3 步 · 在配置页确认并开跑

打开 <http://127.0.0.1:8765> → **配置** → 「渠道登录」确认 5 个 App 都是勾选状态 →
回「监控」点「立即扫描一轮」，然后在「渠道健康 → 三率一险」看这几家有没有出数。

```bash
python main.py      # 或 start.ps1
```

### adb 连不上的四个卡点（按顺序核对）

1. **MuMu 实例真在运行**：多开器里状态必须是「运行中」，不是「已关机」；
2. **MuMu 打开了 ADB 调试**：MuMu 设置 → 其他 → 「ADB 调试」→ 打开，记下端口（默认 **16384**）；
3. **adb 路径对**：`python -m core.setup_check` 的 `App 通路` 行会打印它用的 adb；
   没自动找到就 `--adb "C:\...\platform-tools\adb.exe"`；
4. **端口/序列号对**：`adb devices` 里没出现设备时，用 `--serial 127.0.0.1:<端口>` 显式指定。

> 症状对照：`模拟器在跑但 adb 状态是 absent` = MuMu 服务在、但空调试端口没开或端口不对
> （第 2、4 条）；`找不到模拟器（MuMuManager 不可用）` = 没装或装在非常规目录（第 3 条 + `--mumu`）。

### 已知边界

- App 渠道**只是可选通路**；只采网页渠道时 `App 通路（可选）` 显示「未启用」是正常的；
- 携程 App / 飞猪 App 存在**登录风控**，登不进去时会被人工停手（见 `docs/CHANNEL_PARKED.md`）；
- 设备伪装相关的身份一致性由 `python -m core.android.consistency` 单独体检。

## 这是什么

框架默认只跑 5 个浏览器渠道。App 渠道（智行 / 去哪儿 / 飞猪 / 同程 / 携程 App）是**额外可选**能力：
它们没有可用 Web 面，只能通过 Android App 取数，因此需要本机跑一个
Android 模拟器（MuMu），由框架通过 adb 驱动。

**不启用时，框架行为与以前完全一致**——不 import、不检测设备、不显示 UI。

| 项 | 要求 |

| 虚拟化 | 需开启 VT；MuMu 与 Hyper-V/VBS 可共存（实测 `hyperv_enabled: true`） |
| 磁盘 | 引擎 + 实例约 5 GB 起 |

## 已知限制

1. **登录一次，之后不用再登**：在网页「渠道登录」分区点「App 登录」，
   画面就是真机实时屏幕，点几下完成登录并点「我已登录完成」，程序会把
   `shared_prefs + databases + files` 打包到
   `user_data/android_snapshots/<渠道>.tar.gz`。下次采集前自动恢复，
   换机/重装/清数据后仍是登录态。
   内嵌画面是**近全屏工作台**：默认按视口放大、可切专注（隐藏控制轨）、
   可缩成可拖动浮窗继续操作；画面支持点按/拖动/长按/滚轮，控制轨有内联
   文字输入与返回/桌面/最近/退格；`GET /api/app-login/info?plat=` 只读返回
   分辨率、前台 App 与本次会话统计，供状态栏显示。App 渠道图标使用独立
   squircle 质感层（`.bic-app`，顶高光/底收影）；智行字标已去原图底部
   促销横幅，详见 `docs/ASSET_LEDGER.md`。
   三条保护：设备上的登录态比快照**新**时跳过恢复（不覆盖用户刚登的账号）；
   恢复失败会记 `snap-restore`；**恢复了快照但仍停在登录墙**时会写明
   「快照已失效（需重新登录）」——这是「该重登」而非「该查文件」，两种情况
   必须能分开读。
   **设备上已经登录着，就完全不恢复**：快照是某一刻的副本，用完即旧。
   去哪儿实测：刚登录完导出快照 → 立刻恢复 → App 回到登录墙；不恢复、
   直接重启 → 登录态正常。用旧副本盖掉设备上更新的会话，等于每次采集都把
   用户踢下线（`_looks_blank` 保证白屏中间态不算「已登录」）。
   **导出快照前会先 force-stop**：登录态写在 SQLite（去哪儿是
   `databases/RKStorage`），运行中大部分内容还压在 `-wal`/内存里，边跑边
   打包只会打出一份"看起来有库、其实没有新会话"的旧快照。
   **恢复以 tar 退出码为准**：曾经以输出里有 `DONE` 当成功，而 `echo DONE`
   无条件执行——tar 明明报 `No such file`，恢复却返回「已恢复快照」，设备
   上什么都没变。
   **快照不含动态 so**：`files/plt_dynamic_so` 是 App 自下载的**可执行代码**，
   与设备 ABI 绑定（去哪儿那个是 arm64，模拟器是 x86_64）。带进快照就会在
   恢复时写回设备，App 启动加载即死锁（见下条）。排除后快照从 2.8 MB 降到
   564 KB——登录态本来就只该是凭据。
2. **明细优先，日历兜底**：远期日期（首页 8 天条之外）走「长窗口选日
   → 点查询 → 列表页」拿真实明细（航班号/时刻/价格）。明细解析失败时
   回落到日历价（每天一条最低价、无航班号），并在账本里分开记
   `航班明细` 与 `日历` 两条通路。实测未登录也能拿到明细，遮罩价
   （`￥3??`）才需要登录。
3. **长窗口靠「选择日期」弹层**：首页日期条只有 7–8 天，点开弹层后
   是跨两个月的完整日历、每天有价。入口在首页，**一旦点了「机票查询」
   进列表页就没有日历图标了**——所以流程必须是「设航线 → 停在首页
   → 开弹层选日 → 再点查询」。
4. **弹层价格是异步渲染的**：打开瞬间格子已在但价格为空（实测 2s 后
   才有价），必须轮询到「有价格出现」再读，否则会当成「有日期无价」。
5. **列表页价格被拆成两个节点**：`￥` 与数字是两个独立 TextView，
   不是整串 `¥256`；按整串解析会把整页判成「有航班无价格」。
6. **系统权限框会被自动点掉**：换机/重装后首次启动会弹通知权限，
   它盖在首页上；程序按 activity 判据识别并代点「允许」，不误点正文按钮。
7. **App 卡死（系统「没有响应」）可自愈**：先是「动态 so 与设备 ABI
   不匹配」——App 启动时加载它，主线程 Blocked 在 `Runtime.load0` 等锁，
   **点「等待」186 s 也不恢复**（死锁不会自解）。处置顺序：先点「等待」
   等 30–60 s；仍卡就自己 force-stop 再冷启动（不点「关闭应用」由系统
   乱杀）。根治是让快照别带动态 so（见上一条）。
8. 单设备串行：多个 App 渠道共用一台模拟器，采集是排队执行的。
9. App 改版会导致元素定位失效；届时账本会记具体状态，不会伪装成无票。

## 维度对齐（PC/H5 已有的每个维度都要有）

能力是**声明式**的（`core/channels.py` 的 `CHANNEL_DIMENSIONS`），取值只有
`y` 已验证出数 / `n` 渠道无此能力或停服 / **空 = 产品支持但本仓库采集端
未实现或当前风控未出数（不得当成支持，也不代表渠道没有）**。门禁
`tests/test_r677_channel_dimension_matrix.py` 钉住三条：每渠道每维度必须表态、

### 档位复位：往返 → 单程（去哪儿）

去哪儿首页的「单程/往返/多程」是**持久档位**，跨轮不自动复位。跑过往返
之后接着跑单程，首页仍是往返档：

* 往返日期弹层是**两段式**（先点去程、再点返程、最后「确定」），单程流程
  拿它当单程日历 → 判据永不成立 → `pick-date-failed`，整轮 0 行；
* 更糟的是不报错那条路：结果页是往返页，往返总价被记成单程价。

所以 `_fetch_locked` 一开始就调 `_switch_to_single`，判据是**返程日期位在
不在**（`atom_flight_ll_back_date`）——不用 RadioButton 的 `checked`，实测
同一渲染帧里 checked 会滞后。真机对照：往返跑完后立刻跑 11-06 单程，
复位后拿到 4 条航班、行头 ¥520；不复位时同一条命令直接
`pick-date-failed`。

### 航司代码：数字开头（3U/9C/8L）

`[A-Z]{2}\d{3,4}` 匹配不到「川航3U4553」。真机往返第三张返程卡就是这个
代码，解析出来是空字符串——四个解析器（去哪儿单程/往返、智行单程/往返）
统一改成 `[A-Z0-9]{2}\d{3,4}`，门禁见 `tests/test_r701_qunar_round_trip.py`。


`low_fare` 的落地方式与浏览器渠道同源——它是**发现源**（每天一条最低价），
不是明细：去哪儿 App 首页「低价机票」→ 设城市 → 「搜索低价机票」，登录后
落**原生 RN 页**（`QReactNativeActivity1`），顶部日期带每天一条最低价，横滑
合并 14 天窗口。2026-11-02 真机（已登录）：BJS→SHA 14 天 ¥408/359/450…
（41.2s，`path_note("low-fare","ok")`）；点「日历」后走独立整月解析
（`parse_full_calendar`，日格 `content-desc=q_flight_calendarDayItem#YYYY-MM-DD`），
真机 BJS→SHA 一次 **60 天 / 2 个月（2026-11-02..12-31）**，写
`path_note("日历","calendar", rows=60)`。矩阵 `app_qunar.low_fare/calendar`
均为 **y**；6 天/14 天日期带不再冒充日历。
旧结论「搜索后落 H5 WebView（`HyWebActivity01`）不可读」是未登录/旧流程时
的观测；代码保留 H5 Activity 检测作为异常转场兜底，遇到时记 `unsupported`
而不是 timeout。

智行 App 走首页「特价」页签 → 设出发/到达 + 日期区间 →「搜索特价」，
结果页逐天列出「02.16 周二 ¥1646」，与去哪儿 App「低价机票」**同一契约**
（`core/special_radar.py::_app_qunar_deals` / `_app_zhixing_deals`，
门禁 `tests/test_r732_zhixing_low_fare.py`）。两个页面都**没有写价格口径**
（dump 里没有含税/优惠前/到手任何字样），所以雷达里都标
`tax_included=None` + 「口径未标注」，不假设含税。

智行这条在 2026-11-02 起是**按请求驱动**的（不再只读页面当前选择）：
出发城市是单选弹层；目的地是**多选**弹层（底部 chip，必须清掉旧目的地
再点「确认」，否则会搜成「新加坡，广州」两条航线）；日期是区间长日历
（`YYYY年M月` 标题 + 纯数字日格，默认停在当前选择月，更早月份要向下翻）。
真机样本：北京→广州 11/10-12 三天 ¥520；上海→新加坡三天 ¥843/843/743；
同一表单再跑一遍 18s（只点搜索、不再重设）。驱动失败或日期不在可售窗口
时记空并写明原因，绝不拿旧页面报价冒充请求结果。

> 智行这条早期被记成「目的地低价榜、口径对不上」——那是把首页「省钱攻略」
> 里按目的地报价的推荐卡当成了「特价」档，r732 真机复核已更正为逐天最低价。

`multi_city`（多程）**App 全渠道未接，矩阵标 `""`（产品有入口、
采集未接）；浏览器端仅携程 PC 2 段已生产验证（y，scope 仅 2 段）**，
采集端未实现 = 未验证），不标 `n`——`n` 只留给渠道真没有的能力/停服；
也不写一个不会工作的 `y`。数据模型仍是单 O-D，改造设计见

### 智行 App 的国际档（2026-10-30 真机跑通）

国际与国内是首页上**两个不同的表单**：国际档多出「返程日期」与
「经济/超级经济舱」舱位行，城市选择页的 tab 也不同。`set_flight_route`
按 `is_intl_route(from, to)` 先切档（`select_mode`，判据是该舱位行在不在），
再设城市。不切档就设国际城市时，首页城市位与结果页仍是国内那套。

国际列表页还有一个版式差异：**卡片没有航班号**，只有航司名 + 起降时刻
（国内页有 `CZ8890` 之类）。明细解析因此改成**以「同一排的起飞→到达时刻」
为锚**，航班号退化成可选字段（取不到就留空，绝不编）。

同一改动还收紧了三件事，都是真机踩出来的：

* **经停城市**：中转卡片的「青岛 20h35m」必须落到 `transCity`，否则
  中转会被当成直飞进直飞最优池；
* **行头价取最低直飞**：中转低价不再顶掉行头价（真机：青岛中转 ￥450
  曾把直飞 ￥552 压成行头）；
* **航司名**：机场行（「浦东T2 / 羽田T3」）、排序栏（「比价」）、区头
  （「优选航班」「宠物友好」）都落在同一纵向窗口里，按"第一个中文名"
  取会取到它们；改为优先走"航班号同排左侧"，国际卡再退回"机场行以下"。

实测（MuMu，2026-10-30）：浦东→成田 11-20 / 11-24 各 7 条真实航班
（￥988 起，含起飞与到达时刻），两日期共 60 s；北京→上海 11-05 / 11-06
各 9 条（含 1 条青岛中转，￥450），共 139 s。

### 明细通路的四个坑（r725–r727，全部真机踩出）

这四条都不是"页面变了"，而是**判据把"没看见"当成了"不存在"**：

| 现象 | 真因 | 修法 |
| --- | --- | --- |
| 明细整轮等超时，最后回退日历价 | 点查询后前台换成独立 RN 全屏 Activity（`CRNBaseActivityV2` 的「全网招募：智行机票体验官」），14 行文案 > 旧阈值 12，既判不成广告也不含登录标记 | 营销词 + **无数据**即算广告，文案条数不再设上限 |
| 上一条的 ✕ 点不中 | 关闭钮是私用区字形（`\ue706`），且 y=1092 在页高一半以下（「一键报名」在 1527） | 认图标字形，**只按横向判右侧 2/3**，不限纵向 |
| 设航线记「找不到城市行」 | 冷启动头 4 帧 `dump()` 全是空串（uiautomator 未就绪），`is_intl_form("")` 为 False → 判成「已是国内档」→ 在没渲染的首页上找城市行 | `_await_home`：先拿到首页再谈页面长什么样；空帧只能报「没取到页面」 |
| 某班记成 `984839 ¥2094` | 图标写成 XML 数字实体 `text="&#984839;"`，不还原时 `[A-Z0-9]{2}\d{3,4}` 在字面量里匹配出 6 位数字，还抢在真航班号前被取走 | 解码实体 + 航班号**必须含字母** |

最后一条的判据值得记：纯数字不可能是航班号（`CA8573` / `3U8888` /
`9C8888` 都至少含一位字母），所以"数字正好落在卡片窗口里"不该被当成航班号。

**去哪儿 App 有没有同样的问题**：它的解析器也不还原 XML 实体、正则同样
允许纯数字（`([A-Z0-9]{2}\d{3,4})(?![0-9])`）。但用真机 dump
（`dom_1106_list.xml`，含 `&#986266;` 等实体）实测**没有**串味：它的航班号
候选按「本卡片纵向窗口内」筛选，工具栏图标落在窗口外，取到的是真实航班号。
所以本轮不改它——没有证据就不动；哪天版式让图标落进卡片窗口，先照着
`tests/test_r727_glyph_is_not_flight_no.py` 的思路补行为断言。

真机复验（2026-10-31，SHA→HAK 2027-01-29）：产出 1 条 FlightPrice
（一渠道一日期一行的池约定），`extra` 里 **8 班全部带航班号与时刻**：
CA8573 ¥1734 / MU6355 ¥2085 / FM9253 ¥2085 / MU6381 ¥2085 /
FM9269 ¥2085 / FM9251 ¥2085 / CZ6686 ¥2094 / CZ3516 ¥2094。

## 首次使用（引导）

App 渠道是**可选项**，不会自动启用；**只支持 Windows 10/11 + MuMu**，macOS/Linux 不适用。
推荐按「PC 侧 → 设备侧 → 运行态」三段跑，每段只回答「还差什么」：

### 1. PC 侧：`python -m core.setup_check`

第一行是「运行平台」。重点看三行：

- `App 通路（可选）`：
  - `未启用（只采网页渠道）` = `android.enabled` 总开关还没开；
  - `找不到模拟器` = MuMu 没装/没启动/`android.install_dir` 不对（`--fix` 会自动拉起）；
  - `已连到设备（序列号）` = 通路就绪，后面才是登录与采集。
- `设备环境`：机型/平台/GPU/ABI 是否自相矛盾；高风险按提示跑
  `python -m core.android.consistency`，改完身份用
  `python scripts/identity_boot_module.py` 再重启实例。
- `App 定位`：出厂定位（加州山景城）与出口 IP/时区矛盾是最便宜的风控信号；
  在 `android.geo` 里钉住坐标。

缺依赖 / 浏览器内核 / 配置时，`python -m core.setup_check --fix` 会补齐安全项。

### 2. 设备侧：`python scripts/setup_device.py`

```bash
python scripts/setup_device.py                 # 只读体检：不改设备
python scripts/setup_device.py --apply --reboot
python scripts/setup_device.py --apply --enable-app-channels   # 顺带写入 3 个默认 App 渠道
```

装完自动跑 **12 项体检**（机型、ABI、`/proc/cpuinfo`、SELinux、电话层 RIL/运营商/
网络类型、包名暴露面、Zygisk 注入、模块齐全、隐藏名单、有害模块状态、`mumu_cloak` 启用），
全绿才算准备好。开机后设备伪装需 **2–3 分钟**生效；`--reboot` 会轮询等待，不是固定 sleep。

### 3. 运行态：`python main.py --app-status`

输出五个阶段（检测 / 安装 / 启动 / 装 App / 验证可采集），已完成的打勾。
它**先于实例锁返回**——已有实例在跑时也能查。「验证可采集」只认**真的落过库**，
不拿「已登录」冒充。

最后到配置页打开「Android 真机通道」总开关，并在用户里勾选要采的 App 渠道。

## 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 状态 `not_installed` | 找不到 MuMu | 按 `--app-status` 的提示装，或配 `install_dir` |
| 状态 `stopped` | 实例未启动 | 首轮采集会自动拉起；也可在 MuMu 里手动启动 |
| 状态 `error` + `adb 未连接` | adb 会话断了 | 重开实例；`adb kill-server` 后重试 |
| 账本 `login` | 需要登录 | 页面是登录墙时记此状态；遮罩价（`￥3??`）需登录才显示 |
| 账本 `captcha` | 验证码触发 | 人工接管 |
| 账本 `face` | 人脸/活体核验 | 只能本人操作；本条渠道在该账号下不可自动化 |
| 账本 `timeout` + 「无法识别的页面状态」 | App 可能改版 | 需更新解析器，不是"没票" |
| 账本「N 个目标日期在日历窗口外」 | 目标日期超出两个月 | 缩短监控日期，或等窗口推进 |

## 2026-11-05 · 1260×2800 下的 App 渠道复验与「写死坐标」清算

### 背景

设备屏幕从 900×1600 改到 **vivo X200 Pro 的 1260×2800@453**（为让
`DisplayMetrics` 与机型一致）。这一步代价很大：**五个 App 渠道里所有
按 900×1600 标定的常量全部失效**。本轮逐个渠道复验并改成与分辨率无关
的结构判据。

| 渠道 | 结果 | 最低价 |
|---|---|---|

| `app_tongcheng` | 明细 **4 行** | ¥309 |

### 三条「不能想当然」的教训

1. **不能等比缩放**：飞猪横向 128.6×1.4=180 但实测 171；纵向 144×1.75=252
   但实测 201。比例缩放会让点落进相邻日期/月份 → 一律改成**实测标定表**。
2. **滚动会改变绝对坐标**：日历滚动后月份表头 y 变了，`row0` 必须按
   「实际表头 y + 常量偏移」重算。
3. **`uiautomator dump` 不能走 MuMu shell 兜底**：MuMu 的 shell 在
   `u:r:nemuinit:s0` 域下起不了 UI 自动化服务，`dump` 会**返回 0 节点**——
   而"0 节点"在下游和"页面没这个控件"一模一样，属于**静默错判**。

### 飞猪这条链的专用坑（都已修）

- 首页「机票」原用死坐标 → 读 UI 树；
- 表单 OCR 把档位标签当城市（`dep='单程往返'`）→ 窗口查表 + 排除标签；
- 日历按**表单当前月份**打开（不是当月）→ 先读可见月份、不对就**下滑回翻**
  （左右滑无效）；
- 选完日期还要点**「确定」**（携程不需要）；
- 表单默认停在**往返档**时打开的是**往返日历**（底部「返程：未选择」），
  只点去程不会落定 → 必须先切「单程」档
  （`_ensure_one_way`，本渠道 `supports_round_trip=False`）。
- 停在登录页（`CustomUserLoginActivity`）时记 `login`，不记 `app_path timeout`。

### 生产接入前提（很容易漏）

`main.py` 的 `platforms` 默认值是 `["qunar","fliggy","tongcheng","tuniu"]`，
**全是浏览器渠道**。`users[].platforms` 为空时就走这个默认值，因此
**App 渠道即使跑通也不会进生产轮次**——要启用必须显式加进去，例如：

```yaml
users:
  - name: 邓美銮
    platforms: [qunar, fliggy, tongcheng, tuniu, app_ctrip, app_tongcheng]
```

注意预算冲突：一轮里渠道查询数已接近上限（实测「计划 28 次、实际未发 19 次」），
加 App 渠道会进一步稀释浏览器渠道的上场机会，建议**按航线价值挑选**，不要全加。

### 携程日历：两个「账本上看不出来」的真 bug（2026-11-06 修）

排查 `app_ctrip` 为什么 `航线已设` 之后一直 0 条，挖出两个都在日历滚动上：

**Bug A｜只会前翻，不会回翻**
表单会保留上次查询的日期。生产跑过 `HAK→SHA 2027-02-14` 之后，表单里就
残留 `2027年2月14日`，日历按它打开在 **2027 年 2 月**；下一轮目标
`2026-11-16` 早三个月，而代码只会向上滑（找更晚的月），于是永远滚不到，
记「日历滚动后仍找不到 2026-11-16」。
实测**向下滑 2 次**即可拉出 `2026年11月`。
修法：`cal_scroll_dir(months, y, m)` 按目标相对可见月份决定方向（回到
`tests/test_r1050_ctrip_cal_scroll_dir.py`，含跨年边界）。

**Bug B｜滚动坐标写死 900×1600（影响面更大）**

```python
dev.swipe(450, 1400, 450, 600, duration_ms=400)   # 900×1600 的标定值
```

在 1260×2800 上这段只滑到**屏幕上半部分**，日历主体根本没动 ——
意味着**日历首屏之外的所有日期，携程渠道一直都取不到**。
生产里那些 `航线已设 → 0 条` 很可能就是这个原因。
修法：改成按屏幕比例 `(0.5w, 0.80h) ↔ (0.5w, 0.30h)`。

修复后同航线（SHA→PEK 2026-11-16）恢复 **17 行**完整明细。

> 教训：`.swipe(x1,y1,x2,y2)` 这类**原始像素**调用是 900×1600 残留的高发区，
> 与 `tap()` 的写死坐标同类但更隐蔽——因为滑不动时页面看起来"没变化"，
> 很容易被当成"页面没这个日期"。

### 飞猪 App「国际」维度：卡在阿里 Baxia 滑块（2026-11-06 实测）

**尝试路径**：飞猪表单只有 `单程 / 往返 / 多程` 三个档位，**没有「国际」档**
（OCR 实测 y≈575 只有这三项）。国际只能从**城市页搜国际城市**进。

**实测结果**：设 上海 → 东京 后立刻弹出验证页：

```

XML      = 验证码拦截 / 亲，请拖动下方滑块完成验证 / 向右滑动验证
分级     = strong（confidence 0.95，命中标记 `baxia`）
```

**为什么按纪律不强解**：可见的挑战虽然是几何滑块（本项目 `slider.auto`
就是做这个的），但页面背后是**阿里霸下（Baxia）**——商业级反爬 SDK，
带行为分析；代码里 `_STRONG_MARKS` 明确把 `baxia` 归为强人机，
`slider.classify()` 因此 upcast 成 `strong`、`solvable=False`。
口径：「图像型验证码自动解码尝试（可重试），**行为型强人机不纳入自动尝试**（范围决定，见 `docs/STRATEGY_CONTROL_PLANE.md`）」。

**处置**：该维度如实保持 `intl=""`（未接），命中时记
`app-block / blocked`；`_blocked_reason()` 现在会把
**「滑块挑战」与「白屏安全容器」分开**：

| 形态 | 处置 |
|---|---|
| 滑块挑战（本次） | 提示"需人工拖动一次"——用户拖一下就能继续 |
| 白屏容器 | 只能等冷却或清 App 数据（`scripts/fliggy_app_reset.py --reset --yes`） |

**如果以后要接国际**：可以换一条不触发 Baxia 的入口（例如首页「国际机票」
独立入口），而不是硬解滑块——硬解成功率低、失败还会加重风控，性价比不划算。

**补充实测（2026-11-06 夜，设备空闲时段）**：

1. **首页没有国际机票入口**：UI 树里与「国际/港澳/出境」相关的只有
   `出境游/签证`（x=876,y=1164），OCR 同样只见到这一项。
   飞猪把国际机票藏在「城市页搜国际城市」这条路径后面，没有独立入口可绕。
2. **因此「换入口绕开 Baxia」的方案不成立**——已排除，不必再试。
3. **触发一次 Baxia 后会连累后续**：过掉/重启回到首页后，App 一度可用，

   "当次挡一下"，还会把设备风险分推高一段时间。
   这佐证了"不强解"的选择：强解失败的代价不是一次失败，而是**一段时间内
   整条 App 通道不可用**。

### App 渠道「首启自愈」：清数据/新机后不必人工点弹窗（2026-11-06）

`pm clear` 或换新机后，App 首启会连续弹窗，把首页入口盖住：

```
携程  #1 .permission.ui.GrantPermissionsActivity  「要允许…发送通知吗？」
      #2 ctrip.business.splash.CtripSplashActivity 「同意并继续」
      #3 ...home...HomeActivity                     ← 到这里才可用
同程  #1 com.tongcheng.android/.LoadingActivity     「温馨提示 / 同意并继续 /
                                                     不同意且进入游客模式」
```

原实现只在 activity 含 `permission` 时介入，于是卡在协议页，账本记
「**40s/20s 内未到机票表单页**」——看起来像渠道坏了，实际只差点一下。

已修（`AppCrawler._dismiss_system_prompts`）：按 activity 名分两档处理，
**只在首启类页面上读页面**（避免吃掉广告页序列）：

| activity 含 | 允许点击的文案 |
|---|---|
| `permission` | 允许 / 始终允许 / 仅在使用中允许 / 确定 / 知道了 |

### 重要：价格日历（low_fare）只有在「特价雷达」启用时才跑（2026-11-06 核实）

本会话把 5 个渠道的价格日历都接通并真机验证了（`app_ctrip` 11 行 /
`app_tongcheng` 11 行 / `app_zhixing` 4 行 / `app_qunar` 6 行 /
`app_fliggy` 35 行）。但**它们只在特价雷达里被调用**，而雷达是**显式开启**的：

```yaml
# config.example.yaml 原文：「不配 specials 键即关闭」
specials:
  - from: SHA
    from_name: 上海
    max_price: 400        # 心理价位：低于此值才核实并推送
    days: 30              # 只认未来 N 天内出发
    round_trip: true      # 返程配对
    interval_rounds: 4    # 每 N 轮跑一次发现
```

本机现状：`users[0]` **没有 `specials` 键** → 日志每轮打
`[雷达监控] 跳过 邓美銮（incomplete）` → **价格日历一次都没跑过**。

**这不影响主扫描**：主扫描走 `fetch()`（明细），价格日历只服务于雷达的
「逐日最低价发现」。所以：

- 不配 `specials`：明细类维度（domestic/detail/round_trip）正常，日历类维度休眠；
- 配了 `specials`：才会按上面 5 个源逐日比价、跨渠道核实、推送真低价。

**要启用请明确告知**——它会**开始推送特价提醒**，属于会打扰用户的功能，
不该由采集端自行打开。

### 降低风控触发：硬风控改为长时间冷却（2026-11-06）

风控风险分是**累积**的，而我们原来的行为是"每小时再戳一次"：
`ChannelBreaker` 对 captcha 一律走指数退避、封顶 `breaker_cap_s`（默认 3600s）。

实测到的三种硬拦截都不属于"解个验证码就过去"：

| 现象 | 文案 |
|---|---|
| 携程 | `当前登录环境存在风险，已被限制登录(50003)` |
| 携程（新号） | `当前账号行为异常，已被限制注册(40006)` |
| 飞猪 | `账号风险检测 / 存在1条限制登录风险 / 请完成实名核验` |
| 阿里 | `ContainerActivity` 白屏安全容器 |

改动（`core/pacing.py`）：

- 新增 `_HARD_BLOCK_MARKS`（安全容器 / 限制登录 / 已被限制 / 实名核验 /
  账号风险 / 行为异常 / 环境存在风险 / baxia / ContainerActivity / 无线安全）；
- 新增配置 `crawler.breaker.challenge_cooldown_s`（默认 **21600 = 6h**，
  钳位 0–604800）。命中证据 → 停 6 小时，**且不计 strikes**
  （这不是普通限流，累积次数没有意义）；
- `Pacing.trip` / `ChannelBreaker.trip` / `observe` 全链路透传 `note`，
  判据只用**证据串**，不猜；
- 设 `0` 即退回原来的阶梯退避（`cap_s` 封顶）。

**未受影响的行为**（有回归守着）：普通滑块仍走 `base_s` 阶梯（300s 起）；
登录墙仍走 `login_cooldown_s`（900s）；软拒仍只置 `needs_warmup`。

配置页新增「硬风控冷却」控件（改得动 / 存得住 / 读得回 / 真生效，
受 `test_r634_every_pacing_key_configurable` 管辖）。

回归：`tests/test_r1058_challenge_cooldown.py` 8 项 + 节流/配置整体 **1096 项**。

### 降低风控触发：App 渠道加「每渠道最小间隔」（2026-11-06）

**实测问题**：App 渠道一天被启动 **73 次**，其中 07 时一小时就 24 次
（夜间静默窗结束后的补采）。每启动一次 = 打开 App + 导航 + 读页面，
这是最强的自动化指纹——**越跑越容易被风控**。

**根因**：`crawler.cadence`（每渠道最小采集间隔，分钟）本来是现成机制，
`plan_query` 对所有渠道（含 App）都生效，但**我们的配置里 cadence 是空的**
（`cadence: {}`），等于让 App 渠道跟着 30 分钟一轮的全局节奏跑。
`parse_pacing` 的注释早就写了这条：

> App 渠道也要有 key：它们共用一台设备，节奏通常比浏览器更宽，
> 缺 key 会让调度层在取值时退化成"无节奏"。

**改动**：`config.yaml` 的 `crawler.cadence` 填上 App 渠道 180 分钟
（浏览器渠道保持 0=跟随全局 TTL）。`config.example.yaml` 也补了这 5 个 key
（样例原来只列浏览器渠道，是文档缺口）。

| 项 | 改前 | 改后 |
|---|---|---|
| App 渠道启动频率 | 每轮（30 分钟） | **最少 3 小时一次** |
| 一天启动次数 | ~73 | **个位数** |

**为什么不丢数据**：App 渠道采的是 3 个月后的航线日期，价格变化很慢；
而每次启动要 60–150 秒还占设备。180 分钟是「新鲜度几乎不变、痕迹降一个
数量级」的折中。要更保守可以调到 240–360。

**踩到的坑（已写进回归）**：`config.yaml` 里原本已有一个 `cadence: {}`，
我又插了一个完整的 `cadence:` 块——**YAML 是后者胜出**，写在前面等于没写，
解析出来仍是空字典。`tests/test_r1059_app_cadence.py` 里有一条测试专门钉这个。

**回归**：`test_r1059_app_cadence.py` 6 项 + 节流/配置整体 **219 项**。

### 降低风控触发（二）：自适应轮次退避 + 主采集路径不吃系统代理（2026-11-06）

#### A. 本轮受阻 → 下一轮自动延后

原来 `interval_minutes`（默认 30 分钟）是**死节奏**：不管上一轮被风控拦了
5 家还是全绿，下一轮照常半小时后再来。环境已经不好时，这种节奏本身就是
风险继续累积的来源。

新增 `core/pacing.round_backoff_minutes()`（纯函数）+ `sched_state["backoff_minutes"]`：

| 本轮情况 | 下一轮额外延后 |
|---|---|
| 全绿（trips=0 且无渠道在冷却） | 0（立刻回正常节奏） |
| 1–2 次受阻 | +1 个正常间隔 |
| ≥3 次受阻 | +2 个正常间隔 |
| 封顶 | 240 分钟 |

判据只来自 pacing 自己的记录（熔断次数 + 处于 `challenge`/`ip` 冷却的渠道数），
不引入新口径；**全绿即清零**，所以恢复正常后不会一路慢下去。静默窗的
`wake_at`（剩余秒数）仍取较短值，退避不会把补采推得更晚。

#### B. 主采集路径原来在偷偷吃系统代理（这是个真隐患）

**症状**：日志里 `httpx.InvalidURL: Invalid port ':1]'` 一天出现 45+ 次，
途牛渠道整条空转。

**根因**：`NO_PROXY` 里含带方括号的 IPv6（`[::1]`）时，httpx 0.28 的
proxy_map 会解析失败。而 httpx 默认 `trust_env=True`，所以只要环境里有这个
变量，**每次建客户端就抛异常**。

**更要紧的另一面**：`trust_env=True` 还会把 **Windows 系统代理（本机 Clash
127.0.0.1:7897）** 套到采集请求上。今天已实测到同一个域名一次走上海联通、
一次走**新加坡 AWS EC2**——**国内站点 + 境外出口 = 风控升档的典型特征**。

项目自己在 `crawlers/special.py`、`core/notifier.py` 里早就写着
「系统代理一律不走」「`trust_env=False`」，**主采集路径（new_client）漏了这条**。

**修法**（`core/net.py`）：`new_client` / `get` / `post` 一律默认
`trust_env=False`；显式 `proxy=`（我们自己的出口配置）仍然生效。

回归：`tests/test_r1061_net_no_env_proxy.py` 4 项，其中一条是**负控**——
裸 `httpx.Client()` 在坏 `NO_PROXY` 下必须仍然报错，哪天 httpx 修好了它会
失败并提醒我们复评前提。

### 降低风控触发（三）：修掉"从未成功过的渠道每轮都被跑"（2026-11-06）

**实测证据（今天）**：

| 渠道 | 查询次数 | 有数次数 | 成功率 |
|---|---|---|---|
| tongcheng | 69 | 69 | **100%** |
| fliggy | 40 | 39 | 98% |
| **qunar** | **52** | **0** | **0%** |
| app_zhixing | 43 | 8 | 19% |
| tuniu | 35 | 8 | 23% |

qunar 一天被打了 **52 次、一次都没出数**——纯空转，还在持续消耗 IP 信誉。

**根因是一个判断顺序 bug**（`core/pacing.plan_query`）：

```python
if not last:                       # 没有「成功取价」的基线
    return "fast", "无历史基线"     # ← cadence/TTL 检查都在它后面
```

任何**从未成功过**的渠道都没有 `last`，于是每轮都被判成 `fast` 直接跑，
cadence 与 TTL 全部失效。这不只影响 qunar：`app_qunar` / `app_tongcheng` /
`app_fliggy` 这些"还没在某个航线上出过数"的也一律每轮都跑。

**修法**：

1. cadence 改为按**尝试时间**算（它本来的语义就是「别比 N 分钟更频繁地打
   这个渠道」，按尝试算才对），并提到"无基线"分支**之前**；
2. 新增 `Pacing.note_try(plat, key)` 记录"真的发了请求"（不论成败），
   由 main.py 在 `note_sent` 旁边调用；尝试表上限 4096 条，长跑不涨内存；
3. 判定用 `max(成功时间, 尝试时间)`，有基线的渠道行为不变。

**配置**：`cadence.qunar = 120`（分钟）。保留"限流解除就能恢复"的机会，
但不再每轮空转——一天从 52 次降到个位数。

回归：`tests/test_r1062_no_baseline_cadence.py` 6 项（含"第一次必须能跑"
与"尝试表有界"两条反证）。

### 降低风控触发（四）：连续失败 → cadence 自动升级（2026-11-06）

**实测的浪费集中度**（今天全天）：

| 现象 | qunar | 其他渠道合计 |
|---|---|---|
| 未解析到价格 | 175 | 7（ctrip 5 / tongcheng 2） |
| 三路径空结果 | 130 | 0 |

**一个渠道占了 305 次白打。** 昨天加的固定 `cadence: 120` 不足以压制它——
cadence 是按 `(渠道, 航线, 日期)` 算的，6 条航线 × 每 2 小时 = 72 次/天，
比现状 52 次好不了多少。

**新增规则（对所有渠道生效，不新增配置项）**：

| 连续失败次数 | 生效 cadence |
|---|---|
| < 3 | ×1（配置值） |
| 3–5 | ×2 |
| ≥ 6 | ×4 |
| 任何情况 | 总上限 **720 分钟** |

- 失败计数在 `observe()` 里累加（`hard`/`ip`/`captcha`/`login` 都算）；
- **`soft` 不算**——软拒是"会话没养熟"，是我们自己的功课没做好，不该惩罚渠道；
- 一旦成功（`reset`）立刻清零 → 立刻回到正常节奏；
- 之所以不新增配置键：仓库门禁要求每个 `DEFAULTS` 键都要在配置页有控件，
  而这套阈值属于"策略控制面"范畴（另一条流正在设计 r1063），
  这里先用固定且写清的有界规则，等控制面落地再迁进去。

**效果**：qunar 从"每轮 × 6 航线" → 稳定期 **12 小时探一次/航线**（约 12 次/天）。

回归：`tests/test_r1064_fail_escalation.py` 5 项（含"soft 不算失败"与
"cadence=0 的渠道不受影响"两条反证）。

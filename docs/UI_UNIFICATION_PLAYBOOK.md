## 0. 一分钟速查

如果只有五分钟，读这七条：

1. **用户不会报缺陷名**。「明显不对 / 不跟手 / 没质感 / 收不起来」每一句都能落到具体像素差——本项目十一轮里没有例外。先量，再改。
2. **改前必须有一个坏数字**。只有「改前坏、改后好」的**同一个量**才算证据。说不出差多少 = 还没量到。
3. **统一的对象是「用户需要跨图迁移的动作」**：同一个悬停动作、同一个读数卡、同一个空态。业务语义不同的部分（达标线/K线聚合）保留。
4. **「写了」不等于「生效」**。同优先级后声明胜、`min-height` 顶回 `height`、选择器命中另一条 override——这类缺陷静态断言 100% 绿。凡涉及尺寸/颜色/命中，必须运行时断言。
5. **探针先喂负控**。判据没被已知失败样本打中过，就没有资格判绿。
6. **并行会话在改同一个文件时**：只暂存自己的 hunk；门禁前后比对代码哈希，不一致即作废；红灯先分「值变了 / 设计坏了 / 基础设施」。
7. **全量门禁退出码 3 不是失败**，只说明跑测期间源码被改。判成败看摘要行的 `passed N / failed M` 与 `uitest N/N`。

### 1.2 一条判据成立的四个必要条件

我在这十一轮里作废过至少十条「看起来成立」的判据。能活下来的都必须同时满足：

| 条件 | 反例（我真实犯过） | 正确形态 |
| --- | --- | --- |
| **可测**：读的是渲染值或行为，不是源码字面量 | `assert ".chart-empty{...padding:16px" in src` —— 源码对了但被别处覆盖 | 读 `getComputedStyle` 的 padding |
| **可复现**：换一次运行、换一个并发负载仍是同一个结论 | `wait_for_function` 6s 在并发下等不到 → 假红 | 15s 超时（通过即返回） |
| **能指差多少**：结论带量纲和数值 | 「行高不一致」 | 「13.2px vs 16.5px」 |
| **有负控**：喂一个已知失败样本必须变红 | 死声明扫描器因 `for...of` 拿到 0 条规则而「全绿」 | 注入一条已知失效的声明，扫描器必须报出来 |

### 1.3 判据分层：先问「这条属于哪一层」

不同层的缺陷要用不同层的尺子。混层是误报的主要来源。

| 层 | 典型缺陷 | 尺子 | 工具 |
| --- | --- | --- | --- |
| **符号层** | 函数缺失、旧写法残留、两个分支各写一套算术 | 源码结构 | grep / 字符串断言 |
| **声明层** | 令牌越档、颜色写两份、`<b>` 未写字重 | CSS 声明清单 | 解析 `<style>` |
| **渲染层** | 声明被覆盖、`min-height` 顶回、继承比例行高 | computed 值 | Playwright `getComputedStyle` |
| **像素层** | 落点没画、线糊成一段、图标压字 | 像素块差 / 截图 | canvas `getImageData`、截图裁切 |
| **行为层** | 收不起来、两态坐标不同、热区被邻居抢走 | 事件序列 / `elementFromPoint` | CDP 真实输入 |
| **性能层** | 卡顿、不跟手 | 帧时间 / 单次处理耗时 | rAF 采样、打点 |

**铁律**：符号层与声明层的绿，**不能证明**渲染层与像素层的绿。反过来也一样。一个改动通常需要跨两层断言。

## 2. 技能与协作：三个 skill 在本项目的真实落点

用户这次点名了三个技能。这一章不解释它们「是什么」，只写它们**在本项目里改变了什么行为**——因为空谈方法学对下一轮没有帮助。

### 2.1 superpowers：过程技能优先于实现技能

规则是「过程技能先定方法，实现技能再落地」。翻译成本项目的动作：

| 场景 | 先做（过程技能） | 再做（实现/领域技能） |
| --- | --- | --- |
| 「把这三张图统一」 | **brainstorming**：先定「统一什么/不统一什么」，写进契约表 | 图表内核与 CSS 重构 |
| 「雷达不跟手」 | **systematic-debugging**：先量，定位是落点缺失还是帧率问题 | 修 `hoverDot` |
| 「我改完了」 | **verification-before-completion**：跑门禁并贴输出，不靠记忆宣称完成 | — |
| 「收到 review 意见」 | **receiving-code-review**：先验证意见是否成立，再决定改不改 | 改代码 |

**本项目最容易漏的是第三个**。实测反例：我曾在「改完 + 门禁通过」之后又改了三个文件，然后按记忆报告「全绿」——实际那次全量是 EXIT=3（作废）。**没有当场贴出的输出，等于没有验证。**

反过来也有一条：过程技能不该变成拖延。本项目里 brainstorming 的产出就是 §4 的两张表，一页纸以内；超过一页就是过度设计。

### 2.2 frontend-design：先定设计方向，再写代码

该技能的硬要求是「先出设计计划（色/字/版式/签名元素），自评是否落进通用模板，再动手」。在本项目里它被具体化为四条：

1. **风格已被用户钉死**：微信式扁平（`docs/EXECUTION_SPEC_LATEST.md` §3）。这条 brief 优先于任何「更有冲击力」的方案。**不许自作主张换风格。**
2. **「签名元素」= 走势图本身**。全站只有一个视觉主角/屏（§3.1 第 3 条）。所以走势图的手术必须最细，其他区域保持安静。
3. **克制**：不为「质感」加阴影、渐变、装饰线。本项目的质感来自**节奏（间距阶）、层级（字号/字重四档）、语义色单源、微交互可逆**。
4. **设计必须落到可测项**：见 §3。

**反例（真实）**：我曾把 `.chart-empty` 正文从 13px 改成 12px，理由是「和另两图对齐」。判断错了——13px 是那块**标题档**（初始占位只有裸文本），而契写明「标题 13px 深色、说明 12px 弱色」。**为了「看起来统一」去动字号，是在破坏层级。** 已回退。

### 2.3 multi-agent-workflow：它到底做了什么

这个技能自带一个 `scripts/workflow.py`。**必须先说清它的真实能力**，否则会误以为「跑一下就有多 Agent 干活」：

- `python scripts/workflow.py --task "…"` 输出的是**一份 JSON 建议**：把任务按关键词归到一个角色（内容/研究/开发/审核），列出该角色的能力清单，状态写 `ready_to_execute`，备注「可用于调用外部 spawn 执行」。
- `--split N` 输出 N 条**同名子任务**（`"<task> - 第 i 部分"`），不做语义拆分。
- 它**不启动任何 Agent、不排队、不汇总结果**；`TaskManager` 是进程内内存字典，脚本退出即消失。

所以它的正确用法是**「拆分思考的脚手架」**，不是执行器：

| 用途 | 合适 | 不合适 |
| --- | --- | --- |
| 把一句话任务逼成 3 条能并行的子任务 | ✅ 手工改子任务描述后使用 | — |
| 角色分工的提示（谁写、谁审） | ✅ | 指望它真的派活 |
| 真正的并行执行 | ❌ | 用宿主提供的 Agent 能力 |

**本项目的并行度实际来自三处**（这才是需要治理的对象）：

1. **并行会话**：另一个 AI 会话同时在改 `webui.py`（真实、持续、不可控）；
2. **门禁分片**：`pytest -n` 按文件分组 + UI 自检按 `docs/uitest_profile.json` 的实测权重切 6 片，各自独立起 demo 服；
3. **同会话内派子 Agent**：宿主提供的 Explore / Plan / general-purpose 等。

### 2.4 多 Agent 并行的四条硬纪律

以下四条全部来自真实的、有代价的事故，不是理论。

**纪律一：绝不整文件暂存共享大文件。**

事故：只为提交 1 处修复执行了 `git add webui.py`，把并行会话 **1147 行未提交工作**一起提进了提交。后果是**静默**的——对方下次 `git diff` 看到工作区干净，会以为自己的改动丢了；而提交说明写的是另一件事，review 时无法归因。

正确做法：
```
git show HEAD:webui.py > /tmp/head.py     # 取基线
# 在基线副本上做字面替换（用行内容定位，不用行号）
# difflib 生成 diff
git apply --cached --recount < my.patch
```
提交前必核：`git diff --cached --stat` 的改动行数应等于自己改的行数。看到几百上千行 = 立刻停下。

**纪律二：门禁前后比对代码哈希。**

并行会话可能在门禁运行的 7 分钟里重写 `webui.py`。这样得到的红绿都不可归因。`tools/test_all.py` 已内置：跑测期间源码变化 → **EXIT=3（结果作废）**。

手工跑子集时也要自己做：跑前 `md5sum webui.py`，跑后再比一次，不一致就重跑。

**纪律三：红灯先分清「值变了」与「设计坏了」。**

对方把字号令牌 24/19/16 调成 22/18/16 后，钉死像素的门禁全红。这时有三条路，只有一条对：

| 做法 | 判定 |
| --- | --- |
| 把实现改回去以迁就旧断言 | ❌ 违反设计演进 |
| 把断言改去迁就某个新像素 | ❌ 下次再变又红 |
| 把断言改成**守意图**（`lg > md > sm > 0`、`cozy ≥ 15 且 > compact`） | ✅ |

还有更隐蔽的一种：**门禁钉住的可能正是缺陷本身**。曾有门禁把「把触发器拉成整行」的 CSS 当作断言目标，而那条规则正是本轮要修的缺陷。处置：改门禁，并加一条「该缺陷字面值不得回潮」的反向断言。

**纪律四：区分三种红，只有一种是你的。**

| 类型 | 特征 | 处置 |
| --- | --- | --- |
| **值变了** | 断言里写死的旧数字与新设计冲突 | 改断言守意图 |
| **设计坏了** | 同一现象在渲染/像素层也能复现 | 改代码 |
| **基础设施** | 单跑必绿、复现脚本必绿；或 `ERR_CONNECTION_REFUSED`、`WinError 32` | 放宽等待 / 唯一化临时路径 / 重跑 |

本项目实测的一次归类：某轮 9 项 pytest 红 + 1 项 UI 红，逐条核后**全部**属「值变了 / 设计坏了（但不是我造成的）」——5 项因并行会话把「说明」从诊断卡移进来源条、1 项因把内联内衬改成类、2 项因渠道集合从 5 家扩到 7 家、1 项因独立起服端口未起。**没有一项是并发假红。** 结论必须逐条核，不能一句「并发问题」打包掉。

### 2.5 派子 Agent 的正确与错误用法

| 场景 | 做法 |
| --- | --- |
| 需要跨 6 个文件找「谁在写 `SRX.f.`」 | 派 Explore（只读、快） |
| 需要一个陌生模块的架构结论 | 派 Plan / general-purpose，要求「只读，不改代码」 |
| 需要**同时**改 3 个互不相干的文件 | 只在文件不重叠时并行；`webui.py` 永远串行 |
| 需要「基于调研结果去修 bug」 | ❌ 不要这样派——**不要委托理解**。自己读懂后，把具体文件、行内容、要改什么写进 prompt |

最后一条是硬要求：把「根据你的发现去实现」交给子 Agent，等于放弃了正确性判断。

## 3. 设计语言：微信式扁平怎么变成可测项

### 3.1 六条语法（契约，非建议）

| # | 语法 | 判失败的样子 |
| --- | --- | --- |
| 1 | **表面只有两层**：页面画布 `--bg` / 内容表面 `--card` | 卡中卡、给每条信息一个边框盒 |
| 2 | **分层靠留白与浅底，不靠线**；分隔只用 1px 发丝色，且只在表格行间/必要列表分隔/功能性下缘三类位置 | 给卡片描边、用深色线划分层级；一屏 3 条以上视觉可辨的装饰横线 |
| 3 | **一屏一个视觉主角** | 走势页里有两个抢眼的大数字 |
| 4 | **行式信息结构**：左对象名（13–14px/600）、中次要信息（12px 弱色）、右数值或动作；同类行行高/左缘/右缘一致 | 同一张卡里三行左缘不齐 |
| 5 | **动作写在对象身上**：行级动作在行尾/行头，卡级动作在卡头 | 动作埋进展开体尾部、要滚动才可见、两处同名动作 |
| 6 | **文字即界面**：按钮文案 = 动作结果；折叠一律「展开/收起 + 对象」 | 只有图标没有文字的入口；「更多筛选」与「更多条件」指同一件事 |

### 3.2 五套令牌与它们的实测合规率

令牌的唯一真源是 `webui.py` 的 `:root`。**禁止页面内新造 hex / 新造圆角。**

| 族 | 值 | 实测合规率 | 门禁 |
| --- | --- | --- | --- |
| 圆角 | `--r:14px`（容器）/`--r2:11px`（次级容器）/`--r3:9px`（交互控件）/`--r10:10px`（瓦片）/`--pill:999px`（胶囊）；另有一层 `--r-card:14px`/`--r-container:12px`/`--r-ctl:8px` | 全站 6 视图普查后只剩 1 处非令牌控件圆角（`#srccap .scbtn` 7px），已归 6px | `test_no_non_token_control_radius_remains` |
| 字号 | 10 / 11 / 12 / 13 / 14 / 16 / 17 / 18 / 22 | **99.4%**（827 条 `font-size` 声明） | `test_no_font_size_below_the_smallest_scale_step` |
| 字重 | **只有四档** 400 / 500 / 600 / 700 | 100%（8 视图 × 4017 个文本元素的渲染普查） | `test_font_weight_scale_is_four_steps` |
| 间距 | 4 / 6 / 8 / 12 / 16 / 24（0/1/2/3 属微间距） | **96.9%**（渲染口径：`getComputedStyle` 的 margin/padding/gap，53996 个值，偏离 3.1%） | `test_table_cell_padding_lands_on_the_spacing_scale` |
| 金额 | `--price-lg:22px` / `--price-md:18px` / `--price-sm:16px` | 三档单源 | `test_one_number_tier_for_every_amount_in_the_ui` |

三条容易写错的令牌纪律：

1. **两套令牌并存是实情**（主令牌 `--mut/--line/--card` 与 r364 层 `--r-ink-3/--r-hair/--r-surface`）。新代码用主令牌；改某个区块时该区块本来用哪套就顺着用，**不要跨层混用同一语义**（同一元素既 `--mut` 又 `--r-ink-3`）。
2. **对比度优先于令牌统一**。为达 AA 专门选定的颜色必须保留硬编码。换令牌前两个值都算一遍——实测有颜色换成令牌后从 4.71 掉到 4.38。
3. **`<b>` 必须显式写 `font-weight`**。浏览器默认 `bolder` 是相对计算：父级 600 会算成 **900**，直接冲出四档，而源码里搜不到任何 `900`。全站 4017 个文本元素里曾只有特价日历日期格是 900。

### 3.3 「质感」的四根支柱

用户说「一点质感都没有」时，他指的不是审美偏好。十一轮里「质感差」每次都落在这四根支柱之一：

| 支柱 | 具体含义 | 判据 | 反例 |
| --- | --- | --- | --- |
| **分层的秩序** | 同一种语义只有一层表达；卡里不再套卡 | 统计「卡中卡」数量、「同角色多份定义」数量 | 配额轨颜色写了两份，改一处另一处漂 |
| **节奏的一致** | 同类元素间距同阶；同字号同字重同族 | 间距偏离率、同字号行高集合大小 | 卡片第一段 10px、之后 20px |
| **语义的可辨** | 三种状态用三种**不同色相**，不用同一色相的深浅 | 逐值比对轨道与图例 | 慢档用「浅蓝」表达「被降频」 |
| **微交互可逆** | 悬停/展开/收起都能回到原状态，不留残影、不跳位 | 收起后像素块差归零；两态坐标差 | 雷达浮窗收起后落点留在画布上 |

**这一节的方法论意义**：把「质感」这种主观评价，降解成「分层/节奏/语义/可逆」四个可计数维度。任何一次「没质感」的投诉，先在这四个维度各量一个数，再决定改什么。

### 3.4 什么不是设计语言

| 反模式 | 为什么不算 |
| --- | --- |
| 全部元素加 8px 圆角 + 1px 描边 | 那是「统一了描边」，不是统一了语言 |
| 把字号全改成同一个值 | 破坏了层级（标题档/正文档/辅助档的存在是有理由的） |
| 给卡片加阴影提升「质感」 | 与扁平语言冲突；本项目 9 张卡片全部无边框无阴影 |
| 加渐变/发光做「高级感」 | 抢走视觉主角 |
| 用同一色相的深浅区分三种语义 | 读成「两个状态」，不是三个 |
| 为对齐把左内衬写死 60px | 那不是标签列宽（实测标签列 34+8=42），且右缘贴死 |

### 3.4b 扁平化的边界：什么可以「不扁平」

一味去边框去阴影会把界面做糊。本项目的判定标准是**这个东西需不需要从页面里浮起来**。

| 允许非扁平 | 判据 | 本项目的实例 |
| --- | --- | --- |
| **浮层**：模态、弹窗、悬浮保存条 | 它脱离了文档流、盖在内容之上，必须有可辨识的边界 | `.pvcard`（弹窗，`--sh-pop`）、`.savebar`（右下角浮动保存条，1px `--line2` + `--sh2`） |
| **键帽**：`kbd` | 表达「这是一个可以按的键」，边框是它的语义 | `.kbd` 1px `--line2` |
| **状态色**：达标绿 / 关注琥珀 | 颜色本身承载数据语义，不是装饰 | `.tag`/`.hslot.ok`/`.ws-state.on`/`button.watch.on` |
| **图形徽标内的单字** | 7/8px 字号与描边是图形的一部分，不是可读正文 | `.mark`/`.p`/`.bic` |

反过来，**这些不属于边界，是要清掉的**：

| 要清掉的 | 为什么 |
| --- | --- |
| 给平面卡片加投影或描边「提质感」 | 内容面与画布同层，加边界=伪造层级 |
| 给每一行/每一张卡加下划线 | 分隔交给留白；线只留给表头下缘、必要分组边界 |
| 同一控件既是软底又是投影又是描边 | 一个「选中」用了三个符号 |
| 用 `<i>`/`<em>` 承载状态文本却没写 `font-style` | 浏览器默认 italic，UI 文本会变斜（见 §6 的实测事故） |

**一句话判据**：问「它会不会盖住别的内容？」
会 → 需要边界（投影/描边/更实的底）；
不会 → 必须和内容面同层，不许自己加边界。

### 3.5 设计决策的判据化模板

拿到任何「这里不好看/不舒服」的反馈，按这五问填表，再动手：

```
1) 差在哪一层？      符号 / 声明 / 渲染 / 像素 / 行为 / 性能
2) 同一屏还有谁？    找同角色的其他元素做对照（同族必须同参数）
3) 差多少？          像素/毫秒/色值，写出来
4) 反例是什么？      什么情况下它应该被判失败？（构造一个出来）
5) 改完怎么证？      哪条门禁、哪次实测、哪个数值
```

五问里有任何一问填不出来，说明还在猜。

### 3.6 文案纪律：文案也是设计材料

本项目多次因为「词面」而不是「样式」被判缺陷。以下规则全部有真实判例：

| 规则 | 判例 |
| --- | --- |
| **一个动作全站只有一个名字** | 「更多筛选」与「更多条件」曾是同一件事的两个词；折叠一律「展开/收起 + 对象」 |
| **按钮文案 = 动作结果** | 「收齐」→「已收齐 · N」；点下去后按钮必须换成描述**已发生**状态的字（曾出现点了之后按钮翻成「全部展开」但面板一个像素没动——报了一个没发生过的动作） |
| **计数不能压掉语义** | 事实型 chip（如「组合 2/4」）保留计数为主文本，展开/收起语义放进 `title` + `aria-label` |
| **判据词不许当冗余删掉** | 雷达空态的「监控次数不足」是状态判据词，去重可以去数量，不能删这个词 |
| **口径不明 = 缺陷** | 同一个渠道同时出现 13%（轮次）、76%（查询）、100%（在用查询）——三个都对，错在没有一句口径说明。**数值不一致不是缺陷；没有一句口径说明才是缺陷** |
| **空态是邀请，不是公告** | 空屏要说明「差什么、怎么补」，不能只写「暂无数据」 |
| **不写系统内部名** | 面向用户的文案不出现 `webhook`、`rate_limit` 之类的实现词汇 |
| **失败不道歉、不含糊** | 说明发生了什么 + 怎么修，不用「抱歉」开头 |

**一条元规则**：文案改动会破坏按词面认状态的测试。改文案前先 `grep` 这个词在 `tests/` 与 `docs/uitest.py` 里的引用；有引用就同时改判据，或保留判据词只去冗余。

### 3.7 可访问性底线（不是加分项）

| 项 | 底线 | 实测状态 |
| --- | --- | --- |
| 对比度 | 小字 ≥4.5:1，大字/白字彩底 ≥3:1 | 6 视图 × 2 主题 **0 处不足** |
| 焦点可见 | 每个可聚焦元素在 `:focus-visible` 下有可见环 | 95 个元素 **0 缺失** |
| 触摸热区 | coarse 下 ≥36px | 小控件已从 0 扩展修到 32+伪元素 36 |
| 动效 | `prefers-reduced-motion: reduce` 时全禁（含 `::before/::after`，`*` 不匹配伪元素） | 已实现 |
| 读屏 | 画布内读数也要可达（sr-only live region），离开时清空 | 已实现 |
| 语义 | 不用只有图标、没有文字的入口；必要图标必须有 `aria-label` + `title` | 门禁在册 |

**判据陷阱**：对比度脚本必须认 `color(srgb ...)`（`color-mix` 的输出），否则深色底会被当成无背景；纯符号（`/`、`·`、`—`）不是文字，不该参与 AA 判定。

| 差异 | 位置 | 理由 |
| --- | --- | --- |

**反例（真实且重要）**：r374 曾把「三处走势高度/刻度行数不同」写成「有意保留」。用户实报后实测确认——那是**没统一**，不是差异决策。教训：**「有意保留」只能写进本表，不能留在代码注释里单方面宣布。**

### 4.3 三问判定法

拿到任何一处「两张图不一样」，依次问：

1. **有业务理由吗？** 说不出理由的差异 = 没统一。
2. **同屏能并排看到吗？** 能 → 必须一致（用户会当场看出来）。
3. **用户需要跨图迁移同一个动作吗？** 需要 → 手势、落点、读数必须一致。

三问全否，才允许保留差异，并写进 §4.2。

## 5. 图表内核 PCHART：三条铁律

### 5.1 它不是对象，是共享函数库

最容易误解的一点：`PCHART` 不持有 canvas。各调用点自己持有 canvas/ctx/DPR/指针事件，只把**坐标系、刻度、断档、命中、浮窗定位**交出去。

| 成员 | 职责 |
| --- | --- |
| `prep(c)` | 点集排序/去重、时间轴准备 |
| `niceTicks(mn,mx,n)` | 1/2/5/10 阶梯取整 |
| `domain(vals,padRatio)` | Y 域；单值/同价给最小高度，避免 ±Infinity |
| `frame(W,H,{xKind,n,x0,x1,y0,y1,axisRows})` | 内边距单源 + X/Y 映射 |
| `axes(ctx,frame,{ticks,xTicks})` | 网格与刻度 |
| `area(ctx,frame,pts,{color,gapMin})` | 面积填充 |
| `line(ctx,g,pts,{color,width,alpha,gapMin,dot,vertexDots})` | 折线（含断档分段与顶点） |
| `markMin(ctx,…)` | 最低点标记 |
| `gaps(pts,gapMin)` | 断档分段（中位间隔 × 1.8，不低于 `gapMin`） |
| `pick(g,series,x,y)` | 最近点：先比 \|Δx\|，同刻容差 1.5px 内再比 \|Δy\| |
| `hoverDot(ctx,x,y,color)` | 悬停落点（实心 4 + 卡色光圈） |
| `placeAxis(boxW,boxH,tw,th,localX,topY,rightEdge)` | 浮窗落位算术（唯一一份） |
| `placeTipAxis(host,tip,cx,topY)` | DOM 浮窗落位（含先量再夹、scrollLeft 补偿） |

内边距常量：`PCHART_PAD={L:48,R:16,T:12,B:26,B2:40}`（`B2` 用于双行刻度）。

**调用契约**：`chart()` / `wsDrawChart()` / `spMonDraw()` 只允许构造配置并调用上述函数，不得各自实现坐标、刻度、断档、命中、浮窗定位、空态。

### 5.2 铁律一：一个算术只能有一份

**事故**：关注图 K 线分支自带翻边 `if(left+tw>wrap.width-6) left=px-tw-12`。实测指针 75%→85% 时 left **1028→807（倒退 221px）**，而同一时刻折线分支是 1010→1127 单调递增。K 线浮窗体宽 270（折线 158），越界更早、跳得更频繁。用户读作「悬浮窗乱飘」。

**自检方法**：grep 落位算术的特征串（`left=px-`、`tw-12`、`>wrap.width`、`Math.min(...tw`），任何图体里出现第二份就拆掉。

**推广**：这条不只是浮窗。断档判定、刻度阶梯、最近点命中、颜色取值、渠道名单都有过「两处各写一份」的同族事故。凡是「同一个概念在两处各算一遍」，早晚漂。

### 5.3 铁律二：视觉状态必须可逆

雷达悬停 = 先贴底图 + 画一个落点；收起时还原底图。

```
spMonSnapshot(c)      折线与 K 线各拍一次快照（2 处）
spMonDraw 入口        SPMON.base=null（作废旧快照，防把上一份折线贴回来）
spMonRestore()        每次 hover / 越界 / hideTip 调用
尺寸不匹配            return false，不动画布（否则一次「收起」变成一次全量重绘）
```

**不还原的后果**：画布上留下一个点，读作「停在了别的日期」。

**通用判据**：任何「悬停/展开/选中」的视觉状态，都要能回答「怎么回到原状」，并且验证**回去之后像素与初始一致**。

### 5.4 铁律三：尺寸先量再算，坐标系只用一个源

三条实测教训：

| 坑 | 实测 | 正解 |
| --- | --- | --- |
| 用上一帧的宽度夹右缘 | `innerHTML` 刚换掉时 `offsetWidth` 可能是旧值（158↔169 交替，有一帧读到 166 而最终 169），按 166 夹会让浮窗多越出 3~5px | `Math.max(tip.offsetWidth, tip.getBoundingClientRect().width)`（后者强制同步重排） |
| 忽略 scrollLeft | 容器可横向滚动时，`left` 相对**内容**起点、`getBoundingClientRect()` 相对**可视区**——320 档 scrollLeft=39，浮窗贴左时被裁 4px | `cx-r.left` 加 `host.scrollLeft`（缺失按 0）；右缘用 `Math.max(r.width, host.scrollWidth)` |
| 用 canvas 判越界 | `.mon-chartwrap` 有 10px 内衬，canvas 比容器窄 20px。按 canvas 判：1440 误报 1 次、390 误报 4 次 | 用定位容器（`offsetParent`）当边界 |

还有一条横轴专用：**十字线跟指针，不吸附到采样点**。雷达一天只有几次采集，吸附会让十字线整段停在同一个 x（实测指针 35%/55%/75% 三处恒为 626px），用户读作「不跟手」。读数仍取最近实测点。

### 5.5 四张图的共同点与差异

```
              航线          关注折线        关注K线        雷达折线        雷达K线
坐标系        PCHART.frame  PCHART.frame   PCHART.frame   PCHART.frame    PCHART.frame
断档          PCHART.gaps   同             同             同              同
命中          PCHART.pick   同             同             同              同
浮窗算术      placeAxis     placeTipAxis   placeTipAxis   placeTipAxis   placeTipAxis
落点          hoverDot      hoverDot       hoverDot       hoverDot       hoverDot
位图底座      是            是             是             是（新增快照） 是（新增快照）
空态          有            有             有             有（新增）     有
加载态        有            有             有             有（新增）     有
差异          达标线/区间   目标线/聚焦    OHLC 桶        选中日/最低日   OHLC 桶
```

「四张图」指三处走势里的四个绘制入口：航线、关注折线、关注 K 线、雷达（折线 + K 线）。门禁按「调用点」计数，不按面板计数。

## 6. 缺陷型态库：十六个真实案例

每条都给：**症状 → 判据 → 根因 → 修法 → 改后实测 → 门禁**。遇到同类症状直接对号入座。

### 6.1 悬停零落点

- **症状**：指针在移、图上没有东西跟着动。
- **判据**：悬停前后同一点 15×15 像素块差。改前航线 117 / 雷达 143 / 关注 102——雷达的 143 全来自十字线本身，数据点零变化。
- **根因**：三种写法并存。航线 `arc(...,4.5)` 纯实心（落在线上与线糊成一段）；关注 3.2px 实心 + 1.5px 光圈；**雷达一个都不画**。
- **修法**：抽象 `PCHART.hoverDot`（实心 4 + 卡色 1.5px 光圈），5 处调用。
- **实测**：三图悬停像素块差 143/102/117，移开后归零。
- **门禁**：`test_every_chart_marks_the_hovered_point`。
- **复发信号**：出现新的 `ctx.arc(x,y,3.x...)` 或 `4.5` 落点。

### 6.2 浮窗两种文法

- **症状**：同屏两张读数卡两种形状。
- **判据**：行数 / 高度 / 品牌图标数。改前雷达 2 行 49px、**0 图标**；关注 3 行 69px、2 图标。
- **根因**：雷达自己拼自由文本，而点位上的 `ch` 本来就是真实平台键（ctrip/fliggy/tongcheng 都有官方图标）。
- **修法**：改 `.tm/.tr/.tm` 行文法 + `srxPlatIcon(ch)`；样式只补 `.spmon-tip .tm/.tr` 作用域，**不改** `.ws-tip` 原件。
- **门禁**：`test_radar_tooltip_uses_the_shared_row_grammar`（含「不得再出现 `<br>` 自由文本」）。

### 6.3 图例只解释一部分

- **症状**：画布 7 条线，图例 1 条。
- **判据**：`图例项数 / 画布系列数`。改前 1/7。
- **修法**：`spMonRenderLegend(series)` 接收系列表，补「其他出发日 N 条」（色块与灰线同源）。
- **同批两处**：`.mon-legend>span>b` 缺 `display:inline-block`（色块独占一行，实测色块 y 与文字 y 差 10px）；文案 `'… 选中 ' + ' 11-14'` 拼出双空格。
- **门禁**：`test_radar_legend_covers_every_drawn_series`。

### 6.4 空态：缺行高 + 覆盖层滑出可视区

- **症状 A**：数据不足时画布整块留白，只有一句脚注。
- **症状 B**：320 档空态左缘 **-9px**（容器左缘 30）。
- **根因 B**：`.spmon-kempty` 是 `absolute + left:0`，而容器 `overflow-x:auto`——`left:0` 是**内容坐标**，不是可视坐标。
- **错误解法（我试过）**：改 `sticky`。在 flex 列里它会落到画布**下方**（实测 y=898、画布底 874），多出一块灰板。
- **正解**：absolute + JS 按 `scrollLeft` 写 `left` + 监听容器 scroll 重定位；两条空态分支共用 `spMonPlaceEmpty(el,wrap,W,H)`；宽度取 `min(画布宽, 容器可视宽)`。
- **同批**：`.spmon-empty` 缺 `line-height`（`.chart-empty` 的注释写着「另两图都是 1.6」，规则里只有它自己写了）。
- **门禁**：`test_all_three_charts_show_a_centered_empty_state` / `test_chart_empty_state_shares_the_same_line_height`。

### 6.5 加载态三种形态

- **判据**：首帧 DOM 结构。改前航线是**裸文本**、关注两段、**雷达什么都没有**（先闪一下空画布）。
- **修法**：统一 `<b>正在读取…</b><span>只画真实采集点，未采日期不补点。</span>`。雷达的静态占位挂在 K 线空态覆盖层上，初始必须内联 `display:flex`（CSS 是 `display:none`）；`spMonDraw` **入口**统一收掉，各分支再决定是否重新显示——放入口而不是各分支尾部，才能保证提前 `return` 的路径也不留占位。
- **门禁**：`test_three_charts_share_a_loading_state`。

### 6.6 同字号双行高（「连字体都阶段了」）

- **判据**：按 fontSize 分组统计 lineHeight 的去重数。78 个文字节点、改前两处双档：
  - 12px：按钮默认 `line-height:normal`（13 个）vs 正文 18px；
  - 11px：`.pace-now b i` / `.pace-stat b i` 从 16px 父级继承 1.2 比例算成 **13.2px**，而其余 11px 是 **16.5px**。
- **根因**：继承的**比例**行高不会按子级字号重算「同档」。
- **修法**：只把行高写成绝对值（18px / 16.5px），**不动盒高**。实测面板总高 591→591、行高 44→44。
- **门禁**：`test_pacing_panel_same_font_size_has_one_line_height`。

### 6.7 「声明了但从未生效」——最值得记住的一类

源码读起来完全正确，只有量 computed 值才发现不是设计值。三种成因：

1. **同优先级声明顺序后者胜**：`.hdiag-card .hdiag-acts .btn2{height:26px}` 写在基础 `.btn2{height:32px}` **之前**，自 r433 起从未生效；
2. **`min-height` 把 `height` 顶回去**：连内联 `height:26px!important` 都压不动；
3. **选择器命中了另一条 override**：裸 `.spmon-empty{` 先命中了单条宽度覆盖。

- **修法**：同时写 `height:26px;min-height:26px`。实测自检钮 32→26px、卡片 163.3→157.3px、文本不裁切。
- **通杀法**：CSSOM 死声明扫描器——规则命中 ≥3 个可见元素，且该属性声明值与这些元素的 computed 值**全都不一致** = 从未生效。必须跳过 `@media`（`pointer:coarse` 桌面不命中）与 `var()/%/calc()/auto`。
- **门禁**：`test_small_card_head_buttons_actually_render_at_declared_height`。

### 6.8 三段同色相 + 同一颜色写两份

- **症状**：配额轨读成「深蓝+浅蓝」，与图例写的三档对不上。
- **根因**：慢档段用 `color-mix(--r-blue 40%, --r-surface-3)`——同色相的深浅，不是三种语义。
- **更隐蔽的一层**：`.pace-rail .rs` 与 `.pace-legend .rs` 各写一份颜色，改完轨道后图例仍是旧值（实测轨道琥珀、图例浅蓝）。
- **修法**：蓝 / 琥珀 `--r-amber` / 中性灰，轨道与图例逐值同源。
- **门禁**：`test_rail_segments_and_legend_swatches_share_colors`（逐值相等，不是「都有颜色」）。

### 6.9 两组按钮无分栏：阈值量不出来，要用容器查询

- **症状**：13 个同款灰底按钮只靠 18px 间隙隔开，读成一串，重复的渠道名被当成「同一组列了两遍」。
- **修法**：两组同行时加发丝竖线；**竖线只在同行时有意义**——折行后它挂在第二组左缘、缩进 18px，读作「莫名缩进一格」。
- **关键**：折行由 flex-wrap 决定，**宽度阈值量不出来**（900 档仍同行：宽 340/402，容器 872；768 才折）。必须 `@container (max-width: 780px)` + `container-type:inline-size`。
- **门禁**：`test_tool_groups_are_separated_only_when_on_one_row`（1440/1024/900 有竖线，768/390/320 无）。

### 6.10 TDZ：一行声明顺序让整站 JS 崩溃

- **症状**：`wait_for_function` 20s 超时、`pageerror: Cannot access 'APP_PLAT_NAME' before initialization`、`S` 永不初始化、整站不可用、11 条静态断言全绿。
- **根因**：`const` 声明在首次读取之后。**`typeof X!=='undefined'` 救不了 TDZ**（这是「用 typeof 防未定义」的经典误用）。
- **修法**：声明前移到最早引用之前；裸索引改走守卫访问器；访问器自身保留 `typeof` 兜底（延时回调可能在声明块外执行）。
- **纪律**：UI 测试报 `wait_for_function` 超时时，**先看 pageerror**，不要先怀疑 CPU 争用或测试本身。
- **附带收益**：此项修好后，另一条长期「Playwright 超时」的用例也一起消失——它不是测试坏，是整页脚本没起来。

### 6.11 绿字压绿底：4.32:1

- **判据**：`.spmon-run .st.ok` 用 `--r-green` 压 `--r-green-soft` = **4.32:1**（AA 小字需 4.5）。
- **修法**：改 `--ok-txt`（5.63:1，令牌注释里就是为此准备的）。改后亮/暗两主题 **0 处不足**。
- **普查纪律**：全站 6 视图 × 2 主题一次扫完，不要只修被点名的那一处。

### 6.12 焦点环：搜索页 9/36 缺失

- **判据**：真实按 Tab 后 `matches(':focus-visible')` 为真、但 `box-shadow` 为 none。
- **根因两层**：`.srx-*` 自带 `outline:none`；扁平化的 `.srx-chip{box-shadow:none}` 又把补上的 inset 环清掉。
- **修法**：`#searchview :is(button,a,[role="button"],summary,[tabindex]):focus-visible{box-shadow:inset 0 0 0 2px var(--blue)!important}`。改后 **95 个元素 0 缺失**。

### 6.13 触摸热区：命中区 0 扩展

- **判据**：coarse 下逐元素 `elementFromPoint` 上下探，量「有效可点高度 − 盒高」。实测 `.rngchip` 26px、`.cnav`/`.cc-chip`/`.lgact .btn2`/`#srccap .scbtn` 32px、`.pvx` 28px，**上下各扩 0px**。
- **只加伪元素不够**：实测 `.rngchip` 上方 6px 命中 `DIV.uhead`、下方 3px 命中隔壁 chip——热区被邻居抢走。
- **正解**：触摸档把盒高本身提到 32px，伪元素再补到 36px；桌面 fine 不生效。
- **门禁**：`test_small_controls_get_a_touch_sized_hit_area_on_coarse_pointers`。

### 6.14 卡片双份间距

- **判据**：同容器相邻卡片的实际间距序列。父容器 `gap:10px` + 相邻兄弟 `margin-top:10px` → 第一段 10、之后每段 20，且 20 不在间距阶上（全站普查仅此一处越阶）。
- **修法**：容器内卡片 margin 归零，间距由 gap 单源提供。
- **门禁**：`test_card_spacing_has_no_double_gap`。

### 6.15 说明与触发器分家（r873 的形态，跨会话真实发生）

- **症状**：点「展开说明」，说明出现在整页底部、与触发器之间压着整条卡头。
- **判据**：说明盒是否**整块落在触发器所在的卡内**；说明顶 − 触发器底 ≤ 12px；`elementFromPoint` 命中说明本身；触发器两态坐标差 ≤1px。
- **修法**：把说明移进 `#srccap`，与触发器同卡；收起后卡高回到初始。
- **门禁**：`tests/test_r1130_wave2_health_contract.py`（含负控用例「把说明挪回 `#healthDiag` 直接子级必须判红」）。
- **对本次的启示**：这条门禁上线后，三条老断言（`.healthDiag>#scNote` 的存在性）同时失效——**契约变更会让一整批旧断言过期**，这不是并发假红，要按 §2.4 纪律三处理。

### 6.16 两态坐标不同（「展开时按钮自己跑了」）

- **症状**：点「展开更多条件」，被点的那颗按钮自己移位；收回后也不回位。
- **根因**：展开时面板刚插入、几何未稳，旧实现按当时的 `top-110` 滚动。
- **修法**：下一帧按**控件区顶**对齐滚动；并断言展开/收回两态触发器坐标差 ≤1px。
- **门禁**：`tests/test_r1130_filter_continuity.py`（负控=恢复旧的 30ms/`top-110`，实测 377.9→81.9 低于页头地板即红）。

## 7. 探针纪律：让数字可信

十一轮里最大的时间黑洞不是修 bug，是**被自己写错的探针骗**。下面每条都对应一次「我先得到了一个漂亮但错误的数字」。

### 7.1 十二条工具级陷阱

| # | 陷阱 | 你看到的假数字 | 正解 |
| --- | --- | --- | --- |
| 1 | `for...of` 遍历 `CSSRuleList` | 0 条规则 → 死声明扫描器静默变绿两次 | 索引循环 `for(var i=0;i<rs.length;i++)` |
| 2 | Playwright 序列化箭头函数/闭包 | 扫描函数返回 0 | `add_script_tag` 注入**源码字符串** |
| 3 | `elementFromPoint` 在视口外 | 恒返回 null → 假报「没有命中区域」 | 探测点先夹进视口；越界记为「不可测」 |
| 4 | 2px 步进量热区 | 报 34px（实际可点 54px） | 1px 步进（伪元素边缘余量会让大步进提前 break） |
| 5 | 排查焦点环时一刀切排除 `inset` | 11 个假缺陷 | `inset 0 0 0 2px` 是正规环；只有 `inset 0 -2px`（选中下划线）该排除 |
| 6 | 对比度解析只认 `rgb()` | `color(srgb .13 .31 .64)` 被当成无背景，白字判成 1.11:1 | 补 srgb 分支（0..1 → 0..255）；纯符号分隔符（`/` `·` `—`）不参与 AA |
| 7 | 把「有描边或阴影」当卡片必要条件 | 6 个视图报「0 张卡片」 | 本站是扁平的：按「背景不透明 + 圆角」判 |
| 8 | 隐藏容器里量几何 | `rect=0` 让否定式判据恒真（「无溢出」假绿） | 先证明分支可达，再量 |
| 9 | 程序化 `focus()` | 不触发 `:focus-visible` | 真按 Tab 走一遍 |
| 10 | `Range.getBoundingClientRect()` | 边界含被 `overflow:hidden` 裁掉的文字，误判「没压图标」 | 用盒子右缘减内衬，或直接命中测试/截图 |
| 11 | 合成事件代替真实输入 | 不触发完整 `:hover` 链路 | CDP `Input.dispatchMouseEvent` / `dispatchTouchEvent` |
| 12 | 共用临时文件路径 | xdist 下撞 `PermissionError [WinError 32]` → 随机一项红 | `pid + uuid8` 唯一化 |

### 7.2 三条方法级纪律

**纪律一：负控先行。**
判据写好先喂一个已知会失败的样本。实测有效的例子：注入一张 300px 高、内容 60px 的卡 → tail=222；把 60px 内衬加回 → 极差 19px 报红；把 `srxFacetDirty` 恒返回 false → 10 vs 65 报红。

**负控必须打中守卫真正读的那个对象**。只打中「源码里出现某个关键词」一条，说明行为断言根本没连上产品。

**纪律二：判据别自我否定。**
`'REPLY' in 'NO-REPLY'` 恒真这类，是判据本身坏了。写之前先想「什么情况下它应该是 False」，构造一个出来。

**纪律三：测量环境必须与门禁同模式。**
demo 服量不出真实库的形状（日桶跨度、千行数据）。**探针与门禁必须同时是 demo 或同时是真实**，混用会得出互相矛盾的结论。

### 7.3 一次真实的「假绿」复盘

死声明扫描器第一次跑出「33 条里只有 1 条真缺陷」，我差点据此收工。实际情况：

1. `for...of` 遍历 `CSSRuleList` → 拿到 0 条规则，扫描器返回空 → **报告「无缺陷」**；
2. 改用索引循环后，Playwright 无法序列化箭头函数 → 又返回 0；
3. 改用 `add_script_tag` 注入源码后，才拿到真实的 33 条。

三次里有两次是「工具静默失败」，而失败形态恰好是**全绿**。所以：**任何一次扫描得出「0 处问题」，先问「扫描器真的跑起来了吗」**——用一个已知有问题的样本验一次。

## 8. 门禁编写规范：守意图、锚行为、带负控

### 8.1 锚点三选一，永不选「固定字符窗口」

| 锚法 | 写法 | 适用 |
| --- | --- | --- |
| **函数体边界** | `src[i : src.index("\ndef ", i+10)]` | 断言某函数内的结构 |
| **首条声明** | 取 `sel{` 到下一个 `}` | 断言某条 CSS 规则有某声明 |
| **渲染行为** | 浏览器实测几何/像素 | 断言「真的生效」 |

**我在十一轮里因为固定字数窗口自伤过三次**：`spMonDraw` 的 `+9000` 窗口、`.chart-empty` 的 420 字窗口（我的长注释把它挤出去了）、裸 `.spmon-empty{` 锚点先命中别处的单条覆盖。

规律：**注释越长、窗口越不可靠**。契约变更频率高的函数，一律用函数体边界。

### 8.2 静态与运行时分工

| 断言类型 | 能证明 | 不能证明 |
| --- | --- | --- |
| 静态（读 `webui.PAGE` 字符串） | 结构契约、必须调用的函数、禁止回潮的旧写法 | 是否真的生效 |
| 运行时（Playwright） | 尺寸、像素、命中、颜色、序列 | 代码里是否还有第二份实现 |

**凡是「写了但可能没生效」的，一律要运行时断言**（§6.7 那类缺陷，静态断言 100% 绿）。

### 8.3 断言的三种坏味道

| 坏味道 | 例子 | 改法 |
| --- | --- | --- |
| **钉死像素** | `assert "--price-lg:24px" in src` | 改守意图：`lg > md > sm > 0` |
| **测副本** | 在 spec 里内联一份等价实现去断言 | 断言必须调用产品自己的函数/读产品的渲染 |
| **集合式禁词** | 「不得出现 A / B / C」写死枚举 | 锚语义槽：从源码派生取值全集再逐个比 |

### 8.4 并发基础设施的四个固定动作

| 动作 | 原因 |
| --- | --- |
| 门禁前后比 `webui.py` 哈希 | 并行会话在 7 分钟里会重写它 |
| 条件等待 ≥15s | 6s 在 8 worker + 6 分片时等不到（单跑必绿） |
| 临时文件 `pid + uuid8` | 固定名会在 xdist 下互撞 |
| 失败项逐条归类 | 「值变了 / 设计坏了 / 基础设施」，只有第二种改代码 |

### 8.5 文档与门禁必须双向同步

- 新增门禁 → 同步进 `docs/EXECUTION_SPEC_LATEST.md` §8.4 的清单（**有元门禁校验这份清单本身**：列了不存在的门禁会红，有新门禁没列也会红）。
- 新增契约 → 同步进 §6.6 的表。
- 文档里的每个数值都要能指到代码行或常量名。**文档与代码是两条独立演化线，必须各有一条校验线。**

本项目专门有一组「文档契约门禁」（`tests/test_docs_code_contract.py`，92 项），盯的正是「文档说的 ≠ 代码做的」：令牌值、PCHART 真实成员、表格列数自洽、文档提到的测试文件是否存在、`/api/` 路由是否存在、符号锚点是否失效、历史计数是否标注时效。**改文档后必须跑它。**

### 8.6 我在这份文档上踩过的两个真实陷阱

写本文时，我自己的文档被门禁连挂两次。记下来，因为它们对所有 Markdown 文档都成立：

1. **表格里的 `||` 会被当成列分隔符**。我在一个三列表的某个单元格里写了 `host.scrollLeft||0`，两个竖线让该行变成 4 列，`.test_spec_markdown_tables_are_well_formed` 判红。**修法**：表格内不要写含 `|` 的代码（`||`、`|x|`、位运算），改写成文字描述。
2. **把门禁的「文件名」写成「函数名」**。我先写了 `test_r1130_wave2_health_contract`（没有 `.py`），而该文件里的实际函数叫 `test_note_sits_inside_source_card` 等——读者会去搜一个不存在的函数。**修法**：门禁要么写完整路径 `` `tests/test_x.py` ``，要么写真实函数名并先 grep 确认。

**通用的自查脚本**（写任何技术文档后跑一遍）：

```python
import re, pathlib
doc = pathlib.Path("docs/你的文档.md").read_text(encoding="utf-8")
src = "".join(p.read_text(encoding="utf-8", errors="replace")
              for p in pathlib.Path("tests").glob("*.py"))
missing = [n for n in set(re.findall(r"`(test_[A-Za-z0-9_]+)`", doc))
           if ("def " + n + "(") not in src]
print("不存在的门禁名:", missing)          # 必须为空
```

## 9. 一轮的固定工序

```
0) 记录代码哈希        md5sum webui.py，开跑前后各一次
1) 建基线探针          每句抱怨配一个数字，先量「改前」
2) 逐项修 + 即时复测   一次只改一件事，改完立刻量同一个数
3) 写门禁 + 做负控     变异一次必须红，还原后必须绿
4) 全站扫（不是只修被点名处）
      对比度       6 视图 × 2 主题
      焦点环       全部可聚焦元素（真按 Tab）
      触屏热区     coarse 下逐元素 elementFromPoint
      响应式       9 档宽 × 6 视图
      卡片间距     同容器相邻序列
      死声明       CSSOM 扫描（跳过 @media 与 var/calc）
5) 全量门禁           python tools/test_all.py；哈希前后一致才算数
6) 文档收口           SPEC 契约表 + 本文方法；数值标「当轮快照」
```

**第 4 步是最容易被跳过、也最容易翻车的一步。** 本项目三次「唯一真缺陷」都是全站普查才浮现的：

- `.spmon-run .st.ok` 的 4.32:1（只修被点名处不会发现）；
- 搜索页 9 个焦点环缺失（健康/配置都是 0，只有搜索页有）；
- `#srccap .scbtn` 的 7px 圆角（全站最后一个非令牌控件圆角）。

### 9.1 时间预算参考（实测）

| 阶段 | 用时 | 备注 |
| --- | --- | --- |
| 基线探针 | 15–30 min | 每张图各一个脚本 |
| 逐项修 | 主体 | 一轮 10~14 项 |
| 写门禁 + 负控 | 与修等量 | 负控比门禁本身更花时间 |
| 全站普查 | 30–60 min | 六个普查脚本可复用 |
| 全量门禁 | ~7 min | pytest + 6 个 UI 分片并行 |

### 9.2 诊断决策树：收到「这里不对」时按顺序走

```
① 先复现
   用真实输入（CDP 鼠标/触摸）在 1440 与 390 各做一次
   ├─ 复现不了 → 别猜。可能是「数据形态不同」(demo vs 真实) 或「状态没到」
   │              先换数据再试；仍复现不了，记录「未复现」而不是「无缺陷」
   └─ 复现了 → ②

② 定层（只定一层，不要一次查三层）
   看源码就觉得错？        → 符号层：grep 第二份实现
   声明看着对但观感不对？  → 声明/渲染层：量 computed
   渲染对了但看起来不对？  → 像素层：截图/像素块差
   点了没反应/位置乱跳？   → 行为层：事件序列 + 两态坐标
   动起来卡？              → 性能层：帧采样

③ 找同族
   同一屏还有谁做同一件事？（另两张图 / 同面板其他按钮 / 另一档宽度）
   ├─ 同族都正常 → 这是「单点偏差」，修这一处
   └─ 同族也不同 → 这是「缺统一」，先定契约再一起改

④ 量差多少
   必须写成一个数字（px / ms / 色差 / 次数）

⑤ 定修法（一次只改一件事）
   ├─ 能在单源处修的，不在消费点打补丁
   ├─ 需要新写样式的，先查令牌有没有现成的
   └─ 需要动共享函数的，先 grep 全部调用点

⑥ 立即复测同一个量
   ├─ 没变好 → 判断错了，回退（不要叠加第二个改动）
   └─ 变好了 → ⑦

⑦ 写门禁 + 负控
   负控变异一次必须红；还原必须绿

⑧ 全站普查同类
   只修被点名处 = 只修了冰山一角（见 §9 第 4 步）
```

**最容易走错的三个岔口**：

| 岔口 | 错误做法 | 后果 |
| --- | --- | --- |
| ① 复现不了就当没缺陷 | 直接回「我这边正常」 | 可能是 demo 数据量不足（如日桶只有 1 天），真实数据下必现 |
| ② 一次查三层 | 同时改 CSS 和 JS | 变好了也不知道是哪一步起作用，负控失去意义 |
| ⑥ 没变好就叠加 | 「再试试改这个」 | 两个改动互相掩盖，最后无法归因 |

| **合帧** | 多个指针事件合并到一帧内只处理一次 |
| **钳位 / 翻边** | 钳位=贴到边界就停住；翻边=越过阈值整体跳到另一侧（会造出大跳变，禁止） |
| **行文法** | 浮窗内固定的行结构（`.tm` 时刻 / `.tr` 图标·色点·名称·价格 / `.tm` 明细） |
| **死声明** | 写了但从未生效的 CSS 声明 |
| **TDZ** | 暂时性死区：`const`/`let` 在声明前被引用会抛错，`typeof` 也无法兜住 |
| **负控** | 喂一个已知会失败的样本，验证判据真的会变红 |
| **守意图** | 断言业务关系（大>中>小），而不是断言具体像素 |
| **EXIT=3** | 门禁跑测期间源码被改写，结果作废 |
| **coarse / fine 指针** | 触摸类 / 精确指针（鼠标）；同一控件两档常需不同尺寸 |
| **容器查询** | `@container`：按容器实际可用宽响应，而不是按视口宽 |

## 2. 本会话最重要的方法论

**失败信息几乎总是把人指向错误的根因。先量真实数据，再判断是产品缺陷还是判据太窄。**

这一条在本会话里反复救场。实例：

| 账本说 | 真实根因 |
|---|---|
| 「OCR 未读到日历价」 | 月头左栏界限写死 240px（900 标定），1260 下标题拼不全 → 整图 0 行 |
| 「点日历后日期未变」 | 表单停在**往返档**，打开的是往返日历，只点去程不落定 |
| 「未进入城市选择页」 | 城市页**没有 EditText**（搜索框是文本占位符），但城市列表就在页面上 |
| 「往返日历落点不符：未选择/未选择」 | 底栏解析取了「确定」按钮那一行，没取底栏 |
| 「首页点机票后未到 Flutter 表单」 | 被阿里安全容器拦（白屏），不是坐标问题 |
| 「渠道名压进状态列 413px」 | 手机端是**纵向堆叠**布局，只量水平距离必然误报 |

做法固定为三步：**截图 / dump 词块 / 量 DOM 几何 → 看清页面到底有什么 → 再改判据**。

## 3. 新踩的坑（按形态归类）

### 3.1 「按 900×1600 写死」的清算（本会话最大宗）

设备换成 **1260×2800@453**（让 DisplayMetrics 与机型一致）后，所有旧标定全部失效。
本会话修了 **14 处**，规律：

- **`tap()` 的写死坐标**好发现（点不到）；
- **`swipe()` 的写死像素**最隐蔽（`(450,1400)→(450,600)` 在高屏上只滑到上半屏，
  页面「看起来没变化」→ 被误判成「页面里没这个日期/列表到底了」）；
- **解析器的窗口/阈值**同样致命（`380<=cy<=520`、`x>240`、`col_step=126`），
  它们不报错，只是**静默返回空**。

**判断迁移是否安全：不能等比缩放。** 飞猪实测横向 128.6×1.4=180 但真值 171；
纵向 144×1.75=252 但真值 201。一律改成**实测标定表**（按 `(w,h)` 查）。

### 3.2 测试写死具体日期 → 跨午夜集体失效

`parse_query` 拒绝「开始日期早于今天」。测试里写死 `2026-11-05` 之类，
过了午夜（今天变 11-06）就必然失败，而失败信息看起来像产品 bug。
本会话修了 **3 个**（同程雷达、qunar low_fare、r604 相关）。
**新写测试一律用 `date.today()` 相对日期。**

### 3.3 负控失效比正控失败更危险

两处负控写死了「9 家」「九源官方特价」：
数字一变（9→10），`replace` 落空 → 负控恒过 → **形同虚设**，
意味着正控可能只是「恰好通过」。
**负控必须随当前值取词**（`"%d 家" % n`），不能抄具体数字。

### 3.4 「首页能开」≠「已恢复」

飞猪被风控时，冷启仍能落在 `.home.HomeActivity`（首页是本地页面），
**拦截发生在点进机票模块那一刻**。只看当前 Activity 会误报「已恢复」，
害人白跑。判定必须**真的点一次业务入口**。

### 3.5 同一份文档/矩阵的多处副本必然漂移

改一个 `low_fare: "" → "y"`，牵出 6 处必须同步：
能力矩阵、`DIMENSION_SCOPE`、`DIMENSION_NOTES`、两份交接文档矩阵表、
`APP_CHANNELS.md` 缺口表、`RELEASE_BODY.md`。
仓库的门禁（`test_r805ax` / `test_r903` / `test_r805ae` / `test_release_body_source`）
会逐个抓出来——**它们是资产，不是障碍**。

## 4. 风控与身份（本会话的设备层结论）

- 设备身份（Build / ABI / 序列号 / android_id）**已固定且跨重启不变**；
  改动一次会让阿里系与携程的会话全部失效 → **不要再动**。
- **ABI 首项 x86_64 → arm64-v8a** 已持久化（KernelSU 开机模块 `post-fs-data`），
  系统正常、App 正常；`x86_64/x86` 保留在列表里（否则系统应用起不来）。
- `/mnt/shared`（MuMu 共享目录，名字本身就是特征）**不是挂载点**，
  `umount` 无效；改名成 `/mnt/.sys_share` 即可，已写进开机模块 `service.sh`。
- **nemu 属性**由 `nemud` 周期性写回，运行期每轮开查前动态清（3→6→21 条都见过，
  数量变化是正常的）。
- **Baxia（阿里霸下）属强人机**：可见的虽是几何滑块，但 `_STRONG_MARKS` 判
  `strong` / `solvable=False`。按用户「强人机不做」的要求**不强解**；
  实测强解失败的代价不是一次失败，而是**一段时间整条 App 通道不可用**。
- 携程 50003（登录环境风险）**设备层能做的已做尽**，仍被拒 →
  大概率是**账号风控**维度，建议换账号或等冷却，而不是继续改设备。

## 6. 下一步建议（按价值排序）

1. **飞猪多程**：等 App 可用（人工过滑块 / 冷却）后探一次表单与结果页形态；
   有 `_ensure_mode(dev,"多程")` 可直接切档。
2. **去哪儿同源替换**：`app_qunar` 已验证（明细 1 条 / 日历 6 行 ¥325），
   而浏览器 qunar 长期 0；代价是设备 +约 4 分钟/轮。按昼夜负载取舍。
3. **设备产能**：单设备是硬瓶颈（App 渠道排队 80–150s，3 个 App 渠道时
   单轮 30+ 分钟）。要再提产能只能**加一台模拟器**，不是继续修渠道。
4. **别再动设备身份**（见 §4）。
